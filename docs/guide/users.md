# ユーザプール

## ユーザプールは 1 つだけ

Rolust は、デプロイにつき 1 つのユーザプールだけを管理します（`pool_id`）。ユーザプールの一覧・作成・削除・名前変更・選択はありません。複数のシステムの利用者を分けて管理したいときは、デプロイ（CloudFront・Lambda・DynamoDB のひとまとまり）を分けてください。

## 信頼ポリシーに反映済みの IAMユーザはユーザプールから削除できない

IAM ユーザの削除は、割り当てを一緒に消しますが、信頼ポリシーには触れません。そのため次のどちらかに当たる IAM ユーザの削除は 409 で拒否され、何も消えません。

- そのユーザに、信頼ポリシーに反映済みの割り当てがある（チェックを外したがまだ反映していないものも含む）。削除すると信頼ポリシーには残るのに、どのマトリクスにも出なくなり、Rolust から外す申請も作れなくなるためです。
- そのユーザプールから作った未反映（下書き / 失敗）の申請が、追加または削除するユーザとしてそのユーザを挙げている。削除した後にその申請を反映すると、同じずれが起きるためです。

削除するには、マトリクスでそのユーザのチェックをすべて外して申請・反映し、未反映の申請は反映するか申請履歴で破棄してから削除します。そのロールを削除すると、そのロールの割り当てが削除されるので、そのロールだけが理由で拒否されているときは、ロールを削除してから削除できます（信頼ポリシーには残り、そのロールは Rolust の管理外になります）。

**以前の版で削除した IAMユーザ**は、信頼ポリシーに残っていることがあります。Rolust から外すには、そのユーザを元のユーザプールに登録し直し、マトリクスでそのロールをチェックして申請・反映し（信頼ポリシーには既にあるので変わりません）、続けてチェックを外して申請・反映します。

## 登録する IAMユーザは、反映までに IAM に実在している必要がある

Rolust は、ユーザの登録時に IAM での実在を確認しません（手入力のみを情報源とします。[overview.md](overview.md)）。一方 IAM は、信頼ポリシーの書き込み時に `Principal.AWS` の IAMユーザの実在を検証します（[managed-roles.md](managed-roles.md) の「信頼ポリシーは『空』にできない」）。そのため、IAM に無いユーザも登録と割り当てまでは通り、**反映で初めて**失敗します。IAM が返す原文は次の形です。

```
MalformedPolicyDocumentException: Invalid principal in policy: "AWS":"arn:aws:iam::<ACCOUNT_ID>:user/<ユーザ名>"
```

これは、そのユーザが IAM に無いという意味です。画面には、AWS の原文の前に、そのユーザの ARN と「IAM に存在しないため、信頼ポリシーを更新できませんでした」、直し方（下の 2 通り）が出ます（Issue #208。エラーコードと AWS の原文はそのまま残ります。日本語・英語の画面で本文が切り替わります）。**動作確認などで試すユーザは、先に IAM に作ってから登録してください。** 失敗した申請は申請履歴に「失敗」で残り、AWS 側は変わりません。直し方は次のどちらかです。

- **IAM にユーザを作る**: IAM にそのユーザを作成してから、失敗した申請をもう一度反映します。申請は破棄せず、そのまま通ります。失敗した直後の画面なら、カードの「この申請を再反映」を押します。画面を読み込み直した後や、別の日に戻ってきたときは、申請履歴の「失敗」の行の「再反映」で差分確認の画面を開き、その申請のカードを選択したまま「選択した 1 件を反映」を押します。**ユーザの作成直後は、IAM が新しいユーザを受け付けるまで 10 秒ほどかかります**（実測 3 回とも約 10 秒）。その間の反映は、同じ文言で失敗します。少し待ってから、もう一度反映してください。
- **そのユーザを使わない**: 申請履歴で、失敗した申請を破棄します。続けて、ユーザプールからそのユーザを削除し、申請を作り直します。「失敗」の申請があるロールには新しい申請を作れず、その申請が挙げているユーザはユーザプールから削除できないので（上の「信頼ポリシーに反映済みの IAMユーザはユーザプールから削除できない」）、破棄が先です。

IAM に無いユーザが複数あるとき、IAM が報告するのは 1 件だけです（`Principal.AWS` の配列の先頭の 1 件。実測）。直して再反映したあとに、次のユーザが同じ形で報告されることがあります。ユーザではなくロールが IAM に無いときも、IAM の原文は同じ形ですが、Rolust は「ユーザが存在しない」とは言わず、AWS の文言をそのまま出します。

## ユーザプールは削除できない

ユーザプールは固定の 1 つなので、削除する操作はありません。過去の申請は、凍結入力にユーザプールの識別子を持ったまま申請履歴に残ります。画面にはユーザプールを表示しません。

## ユーザプールに登録できるのは、許可したアカウントの IAMユーザだけ

ユーザプールに登録できる IAMユーザの AWSアカウントID は、SSM パラメータ `/rolust/allowed-account-ids`（String。デプロイ先リージョン）に置いた許可リストに限られます。**apply 直後の値は、デプロイ先のアカウント ID だけ**です。別アカウントの IAMユーザを使うときだけ、アカウント ID を足してください。

```bash
# 展開先のルートで実行する
terraform -chdir=infra output -raw set_allowed_account_ids_command    # 実行すべきコマンドを表示する（下と同じ内容。export 行も含む）

export MSYS_NO_PATHCONV=1                                # Git Bash で '/rolust/allowed-account-ids' がパスに変換されるのを防ぐ
aws ssm put-parameter \
  --region ap-northeast-1 \
  --name '/rolust/allowed-account-ids' \
  --type String \
  --overwrite \
  --value '<デプロイ先のアカウント ID>,<追加するアカウント ID>'
```

- 書式は、12 桁のアカウント ID のカンマ区切りです（空白は無視されます）。**デプロイ先のアカウントも、使うなら含めてください**（上書きなので、含めなければ外れます）。
- **検証する入口**: 「ユーザを新規登録」（1 件ずつ・CSV）と、ロールを新規登録するときの信頼ポリシーからの取り込みです。許可外のアカウントのユーザを新規登録すると、400 で拒否され、何も書かれません。
- **ロールを新規登録するとき**、信頼ポリシーに許可リストに無いアカウントの IAMユーザがいても、ロールの登録は止まりません。そのユーザだけ取り込まず（登録も割り当てもしません）、成功通知に件数が出ます。信頼ポリシーには管理外のプリンシパルとして残り、差分確認の警告に出ます。あとから許可リストに足したときは、ユーザは「ユーザを新規登録」で登録できます。割り当てを信頼ポリシーから取り込み直すには、ロールを削除して登録し直します（割り当てごと消え、AWS 上のロールと信頼ポリシーは変わりません。登録済みのロールの再登録は 409 です）。ユーザを登録したあとに、そのユーザだけを信頼ポリシーの現状に合わせて記録へ取り込むなら、割り当てを消さずに済む「記録を IAM に合わせる」も使えます（IAMロール管理画面の「信頼ポリシーを確認」で出る乖離の詳細から。[managed-roles.md](managed-roles.md) の「信頼ポリシーの乖離を直す」）。
- **値が無い・空・書式不正・取得不能のときは、IAMユーザを新規登録できません**（502。設定の誤りが、黙って制約を外さないため）。ロールの登録は、未登録の IAMユーザが信頼ポリシーにいるときだけ許可リストを読みます。
- 変更が効くまで **最大 5 分**かかります（Lambda 内のキャッシュ）。
- **すでに登録した IAMユーザには影響しません。** あとから許可リストを外れたアカウントのユーザも、登録と割り当てはそのままで、新しい登録だけが拒否されます。
- IAMロールのアカウント ID には、この許可リストは適用しません（別アカウントのロールを使えるかは、ターゲット側の Reader・Manager の有無で決まります。[cross-account.md](cross-account.md)）。

`--name` を既定値から変える場合は、Terraform の変数 `allowed_account_ids_parameter_name` を同じ値にしてください。
