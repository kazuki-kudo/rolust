# 管理対象のロール

## 管理対象は IAMロールのタグで絞り込まれる

apply / diff Lambda の実行ロールが `iam:GetRole` / `iam:UpdateAssumeRolePolicy` を持つ範囲は、**ロールに付いたタグ**で絞り込まれています。

```
Resource:  arn:aws:iam::<account>:role/*
Condition: StringEquals { "aws:ResourceTag/<managed_tag_key>": "<managed_tag_value>" }
```

**`Resource` が `role/*` であることだけを見て「絞り込みが無効」と読まないでください。** 実効的な絞り込みは `Condition` が担っています。タグ方式では `Resource` を先に絞ることが原理的にできない（タグは読んでみるまで分からない）ため、この形が正常です。

| 変数 | 既定値 |
|---|---|
| `managed_tag_key` | `rolust:managed` |
| `managed_tag_value` | `true` |

同じ値が Lambda の環境変数 `ROLUST_MANAGED_TAG_KEY` / `ROLUST_MANAGED_TAG_VALUE` として渡り、**ロール登録（画面 2）の入力検証にも使われます**。タグが無い、値が違う、ロールが存在しない、対象が Rolust 自身の実行ロールである（2026-10-24 追記） — いずれも登録の時点で `400` になり、何が問題でどう直せばよいかがモーダル内に表示されます。反映まで進んでから `AccessDenied` で気づく、ということは起きません。

登録画面は、対象ロールに必要なタグを送信前に表示します。ただし**画面側で事前に合否を判定することはできません**。タグは AWS 上のロールにしか存在せず、ロール名からは判別できないためです。判定はサーバが `iam:ListRoleTags` で行います。

### 対象ロールにタグを付ける

```bash
# 登録したいロールにタグを付ける（運用者の作業）
aws iam tag-role --role-name <ロール名> --tags Key=rolust:managed,Value=true

# 付いているか確認する
aws iam list-role-tags --role-name <ロール名>
```

現在のタグと許可範囲は apply 後に確認できます（展開先のルートで実行します）。

```bash
terraform -chdir=infra output -raw managed_role_tag        # => rolust:managed=true
terraform -chdir=infra output -raw managed_role_arn_scope  # => arn:aws:iam::<account>:role/*
```

タグは API からも読めます（登録時検証が返す 400 の本文にも含まれる値です）。

```bash
curl -u <user>:<password> https://<distribution-domain>/api/config
# => {"managedTagKey":"rolust:managed","managedTagValue":"true"}
```

**この方式が持ち込む制約:**

- **管理対象の増減は Terraform の外で起きます。** タグを付けるのは運用者であり、Rolust は `iam:TagRole` を持ちません。したがって管理対象が増えたことは `terraform plan` にも CI の `plan-guard` にも現れません。**統制点は `iam:TagRole` を持てる人が誰かに移ります。**
- **タグを外せば管理対象から外れます。** 逆に、タグを付けられる者はアカウント内の任意のロールを Rolust の管理対象にできます。この方式の防御力は、`iam:TagRole` の配り方に依存します。
- 照合は `StringEquals` による**完全一致**です。`rolust:managed=True` は `rolust:managed=true` に一致しません。
- **接頭辞方式にあった構造的な防御層が 1 つ失われています。** 以前の既定値 `RolustManaged-` は大文字始まりで、`project_name` が英小文字始まりに制約されるため Rolust 自身の実行ロールと**原理的に**前方一致しませんでした。タグはどのロールにも付きうるため、この層はありません。残る防御は `DenySelfEscalation`（`infra/lambda.tf`）の明示 Deny のみで、**単層の最終防衛線**になっています。Rolust が作る 5 つの IAMロール（Lambda の実行ロール `rolust-crud-exec` / `rolust-diff-exec` / `rolust-apply-exec` / `rolust-edge-auth-exec` と、API Gateway のサービスロール `rolust-apigw-logs`）への `iam:UpdateAssumeRolePolicy` は明示的に Deny されます。`rolust-apigw-logs` は API Gateway サービスが引き受けるロールで Rolust のコードは引き受けませんが、Rolust が作るロールはすべて一律に Deny の対象にしています（誤って管理対象タグが付いても Rolust 経由で信頼ポリシーを書き換えられないようにするため）。**この 5 つのロールは、画面 2 から登録することもできません**（2026-10-24 追記。同じ一覧が Lambda の環境変数 `ROLUST_SELF_ROLE_ARNS` として渡り、登録の時点で `400` になります）。Deny だけだと、誤って管理対象タグを付けた場合に、登録・申請まで進んでから反映で `AccessDenied` になるためです。
- **CRUD Lambda がアカウント内の全ロールのタグを列挙できます。** 登録時検証（`iam:ListRoleTags`）を成立させるために `Resource: role/*` を条件なしで取っています。読み取り専用であり AWS の状態を変える能力は持ちませんが、無関係な他システムのロールを含む偵察情報にはなります。これは受容したリスクです（`infra/lambda.tf` の `crud_iam_read_tags` に記録）。また、ロールの登録時に、管理対象タグの付いたロールの信頼ポリシーを読めます（`iam:GetRole`。Diff Lambda と同じ範囲。`infra/lambda.tf` の `crud_iam_read_trust`）。
- **登録時にロールの実在を確認します。** 存在しないロールは登録できません。Rolust は、ユーザについては実在確認をしませんが、ロールについては登録時に実在を確認します。タグは AWS 上にしか存在せず、読まずに判定できないためです。

**残る帰結:** タグが付いた範囲では、**管理画面に到達できる者はその範囲の任意ロールの信頼ポリシーを書き換えられます。** 管理画面（Basic 認証）の防御力が、そのままタグ付きロールの信頼ポリシー改変権限の防御力になります。poc であることを踏まえ、**本番アカウントへの導入は推奨しません。**

## 信頼ポリシーは「空」にできない — プレースホルダが自動で入る

IAM の信頼ポリシーは空を表現できません。`Statement` は最低 1 件必要で、`Principal` も非空でなければならず、`Principal.AWS` の IAMユーザ ARN は**書き込み時に実在検証**されます。

そのため、Rolust が管理するプリンシパルだけで構成されたロールから**最後の 1 件を削除する**と、そのままでは `Statement` が 0 件になり `MalformedPolicyDocumentException` で反映が失敗します。これを避けるため、Rolust は次の Statement を自動的に挿入します。

```json
{
  "Sid": "RolustPlaceholder",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::<account-id>:root" },
  "Action": "sts:AssumeRole",
  "Condition": { "DateLessThan": { "aws:CurrentTime": "1970-01-01T00:00:00Z" } }
}
```

条件が恒久的に偽なので、**誰もこのロールを引き受けられません**。root をプリンシパルに使うのは、IAM が実在を検証する以上、常に実在する唯一の選択肢だからです。条件が偽である限り root に権限は渡りません。

`Effect: Deny` ではない点が重要です。明示的 Deny は後から Rolust が追加する Allow に**勝つ**ため、Deny のプレースホルダを置くとロールが恒久的に引き受け不能になります。

プレースホルダの出し入れは次のとおりです。

- **挿入するのは `Statement` が 0 件になるときだけです。** 管理外の Statement（サービスプリンシパルなど）が残る場合、IAM はその文書を受け付けるため挿入しません。
- **ユーザを追加する申請を反映すると、プレースホルダは自動的に取り除かれます。** 識別は `Sid: RolustPlaceholder` だけで行います。この Statement に手で書き加えたプリンシパルも一緒に消えます。
- **プレースホルダは管理外プリンシパルの警告に出ません。** Rolust 自身の Statement だからです。差分確認画面（画面 4）では、反映がプレースホルダを取り除く・挿入するときに、カード内の注記で示します。

**管理対象ロールを空の状態から始めたい場合**も、同じ形の Statement を手で置いてください（`aws iam create-role` に渡す例は、[setup.md](setup.md) の「参考: 空の信頼ポリシーのロールを作る」にあります）。IAMロールは信頼ポリシーなしでは作成できません。`Sid` を `RolustPlaceholder` にしておけば、最初のユーザを追加したときに Rolust が取り除きます。

## 管理対象ロールを Terraform で作る場合

Rolust が信頼ポリシーを書き換えるため、**Terraform に `assume_role_policy` を管理させてはいけません**。そのままにすると次の `terraform apply` が Rolust の反映を巻き戻します。

```hcl
resource "aws_iam_role" "managed" {
  name               = "Example"
  assume_role_policy = jsonencode({ /* 初期状態のプレースホルダ */ })

  # 管理対象であることはこのタグが決める。名前は関係しない。
  tags = {
    "rolust:managed" = "true"
  }

  lifecycle {
    ignore_changes = [assume_role_policy]
  }
}
```

`infra/` が作るのは Rolust 自身の実行ロールだけなので、この設定は含まれていません。管理対象ロールを IaC で作る場合に必要になります。

## ロールの登録 — そのままユーザプールに紐づき、信頼ポリシーの IAMユーザが取り込まれる

**登録＝紐づけ**: IAMロールを新規登録すると、そのロールはIAMロール割り当ての末尾の列になります。「ロールの紐づけ」の操作はありません。列の並び順は、IAMロール画面の「並び順を編集」で、まとめて変えて保存します（AWS へは書き込みません。保存するまで、元の並びのままです）。

**登録のとき**: タグの検証の後、Rolust はそのロールの信頼ポリシーを読み（`iam:GetRole`。管理対象タグの付いたロールだけ）、`Effect: Allow` の Statement にいる IAMユーザを、ユーザプールの IAMユーザと、反映済みの割り当てとして取り込みます。マトリクスには、チェック済みで出ます。成功の通知に、取り込んだ件数（うち新規登録の件数）が出ます。

- **取り込む対象**: `arn:aws:iam::<12 桁>:user/<名前>`（パスなし）の IAMユーザ。別アカウントのユーザも取り込みます。ユーザプールに未登録なら IAMユーザを作り、登録済みなら作りません。`Condition` 付きの許可も取り込みます。そのユーザのチェックを外して反映すると、条件付きの Statement からも削除されます。ARN は大文字小文字を区別して照合するので、大文字小文字だけが違うユーザは別のユーザとして登録されます。
- **取り込まない対象**: パス付きの IAMユーザ、ロール、サービス、アカウント root、ワイルドカード、`Deny` のプリンシパル、削除された IAMユーザ（信頼ポリシーには一意 ID `AIDA…` として残ります）。これらは、差分確認で、これまでどおり管理外として警告されます。
- **読めないとき**: 信頼ポリシーを 1 件でも読めなければ、何も変えずに登録を拒否します（AWS のエラーコードが表示されます）。管理対象タグが外れたロールは `AccessDenied` になるので、タグを付け直してください（「対象ロールにタグを付ける」）。`terraform apply` の直後は、IAM の反映が遅れて拒否されることがあります。何も書かれないので、少し待って、もう一度登録してください。
- **デプロイ先と別アカウントのロール**も、ターゲット側の Reader を引き受けて信頼ポリシーを読み、同じように取り込みます（[cross-account.md](cross-account.md)）。Reader を引き受けられないときは、何も変えずに拒否します（AWS のエラーコードと直し方が表示されます）。
- **登録済みのロール**をもう一度登録すると、何も変えずに 409 になります（取り込みは、反映済みとして割り当てを書くので、登録済みのロールに行うと、未反映のチェックを上書きしてしまうためです）。
- **失敗したとき**: 登録の途中で失敗すると、そのロールは登録されないまま（一覧にもマトリクスにも出ません）、取り込み済みの IAMユーザが残ることがあります。同じ登録をもう一度行うと続きから直ります（何度実行しても同じ結果になります）。ロールは、最後に確定するので、「登録されているのに紐づいていない」状態にはなりません。

**既存のロールは取り込み直されません。** 登録済みのロールの割り当ては、マトリクスで作った記録のままです。信頼ポリシーと記録を合わせ直すには、未反映のチェックを反映するか破棄し、ロールを削除して、登録し直します（削除のときに、未反映のチェックは削除されます）。割り当てを消さずに、乖離したユーザだけを信頼ポリシーの現状に合わせるなら、「記録を IAM に合わせる」も使えます（下の「信頼ポリシーの乖離を直す」）。

## 信頼ポリシーの乖離を直す — 「IAM を記録に合わせる」と「記録を IAM に合わせる」

IAMロール管理画面の「信頼ポリシーを確認」で乖離が見つかったロールは、「詳細」のモーダルから、ロール 1 本ごとに、次の 2 つの操作のどちらかで直せます。どちらを正とするかは、操作する人が選びます。どちらも、押した時点で Rolust が信頼ポリシーを読み直して乖離を計算し直します（画面の確認結果は使いません）。管理外のプリンシパルとプレースホルダには触れません。

| | IAM を記録に合わせる（申請を作成） | 記録を IAM に合わせる |
|---|---|---|
| 正とするもの | Rolust の記録（反映済みの割り当て） | IAM 上の信頼ポリシーの現状 |
| 使う場面 | 信頼ポリシーが Rolust の外から改ざんされた・誤って変えられた | Rolust の外からの変更が正当だった（記録のほうを実態に合わせたい） |
| 起きること | 乖離を入力にした**下書きの申請**を作り、差分確認の画面へ移る。反映を指示するまで、AWS は変わらない | Rolust の記録（割り当て）だけを更新する。**AWS の信頼ポリシーは書き換えない** |
| 権限 | 申請の作成は `editor` 以上。反映は `applier` | `editor` 以上 |
| 未反映の申請（下書き・失敗）があるロール | 作れない（理由と申請 ID が出る。申請を反映するか破棄してから） | 実行できない（同じ） |
| 履歴 | 申請履歴に「乖離の修復（IAM を記録に合わせる）」の申請として並ぶ | 申請履歴に「記録の取り込み（AWS は書き換えていません）」の申請（状態は反映済み）が、実行者つきで並ぶ |

- 「記録を IAM に合わせる」は、押すと同じ詳細の画面が確認の表示に切り替わり（別のモーダルは開きません）、「キャンセル」と「記録を合わせる」で選びます。記録に取り込む・記録から外すユーザの ARN が出ます。**そのユーザの未反映の編集（マトリクスで付けたチェックの変更）は上書きされます。** 乖離したユーザの交点だけを書き、ほかの交点は変えません。
- 「記録を IAM に合わせる」の途中で一部の記録を更新できなかったときは、失敗したユーザが列挙されます。もう一度実行すると、乖離を計算し直して残りを直します。
- 「記録を IAM に合わせる」が全件成功すると、そのロールの行は「再確認が必要」になります（確認の結果は、操作では自動で更新されません）。「信頼ポリシーを確認」をもう一度押すと、「一致」になったことを確かめられます。
- 対象は、ユーザプールに登録済みのユーザの乖離だけです。未登録のユーザ・許可リストに無いアカウントのユーザ・管理外のプリンシパルは、乖離に数えず、どちらの操作でも取り込みも削除もしません。

## IAMロールの削除 — 割り当てごと消え、AWS 上のロールと信頼ポリシーは変わらない

IAM ロールを削除できるのは、未反映（下書き / 失敗）の申請が無いときだけです。残っていると、一覧の「削除」で開く確認に理由と直し方が出て、API（`DELETE /roles?arn=<ロールの ARN>`）も 409 を返し、何も消えません。未反映の申請は反映するか申請履歴で破棄してください。ユーザプールへの紐づきは、削除できない理由になりません。割り当て（チェックありまたは反映済み。未反映の変更を含む）が残っているときは、確認に件数（うち未反映の変更の件数）が出て、「割り当てごと削除」で、そのロールの割り当てもすべて消えます。IAM ユーザはユーザプールに残ります。

削除は Rolust の記録（ロール・紐づけ・割り当て）だけを消します。**AWS 上の IAMロールと信頼ポリシーには触れません**（Rolust の実行ロールは `iam:DeleteRole` を持ちません）。削除したロールは Rolust の管理外になります（マトリクスの列にも申請にも出ません）。

- **信頼ポリシーから Rolust の IAMユーザを外したいとき**は、削除の前に、IAMロール割り当てでチェックを外して申請・反映してから、削除してください。
- そのロールの申請は申請履歴に残ります。**同じ ARN で登録し直せ**、そのときは、削除前の申請もそのロールの申請として表示されます（申請履歴はロールを ARN で表示します）。
- 削除は、「紐づけ → 割り当て → ロール」の順に消します。途中で失敗すると、ロールは登録されたまま残ります（マトリクスの列には出ません）。もう一度削除すると続きから片付きます。
