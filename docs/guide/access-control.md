# 認証とアクセス制限

[English](en/access-control.md) | **日本語**

## 認証方式の選択

管理画面と API の認証は、`auth_mode` で選べます。既定は `basic`（単一の資格情報の Basic 認証）です。複数の管理者がそれぞれの資格情報でサインインするには、`cognito`（Amazon Cognito のユーザープール）を選びます。どちらでも、IP 許可リスト（下の「IP アドレス制限」）の判定が認証の前に行われます。

1. `terraform.tfvars` に `auth_mode = "cognito"` を書いて apply します（[setup.md](setup.md) の「Terraform 変数を用意する」と「apply する」と同じ。**最初の apply の前に書いておけば、切り替えの 503 は起きません**）。**既に `basic` で apply 済みの環境で切り替えるときは、切り替えの間と、反映後の最大 5 分（Lambda@Edge のキャッシュ）は、どのアクセスも 503 になりえます。** Cognito は CloudFront の更新の後に作られ、サインイン画面が使えるまで数分かかります。
2. 以後の `terraform plan` と `terraform apply` のすべてで、同じ値を使ってください。`terraform.tfvars` に書いてあれば足ります。`-var` や環境変数で渡す場合も同じ値にします。値が `basic` のままだと、Cognito の破棄が差分として出ます（plan-guard は、この破棄を赤信号にしません。plan の差分を目で確かめてください）。
3. **ユーザの追加**（作った後に、権限のグループを割り当てます。次の「管理者の権限」）: `terraform -chdir=infra output -raw create_cognito_user_command`（展開先のルートで実行します）が実行すべきコマンドを表示します。`<...>` を置き換えて実行してください。メールアドレスは検証済み（`email_verified=true`）で登録します。
   - **一時パスワードは自分で決めません。** 出力されるコマンドの `--temporary-password` は、コマンドの中で乱数から作られます（`printf '%sAa1!' "$(openssl rand -base64 12 | tr -dc 'A-Za-z0-9')"`）。12 文字以上で、小文字・大文字・数字・記号をすべて含むので、パスワードポリシーを満たします。値は画面に出ず、Cognito が登録したメールアドレスに送ります。手で書き換えるときも、一時パスワードにパスワードポリシーが掛かります。満たさないと `InvalidPasswordException`（`Password did not conform with password policy`）で失敗し、Cognito は違反を 1 つずつしか返しません。
   - 一時パスワードは、Cognito が登録したメールアドレスに送ります（件名は `Your temporary password`）。
   - 初回のサインインで、新しいパスワードの設定を求められます（同じポリシーです）。
   - **ユーザを作っただけでは、何もできません。** 続けて、権限のグループ（`viewer` / `editor` / `applier`）のどれか 1 つに割り当てます（次の「管理者の権限」）。割り当てるまでは、サインインしても「操作できる権限がありません」になります。
4. **パスワード**: 本人が変えられるのは、初回の強制変更と、サインイン画面の「パスワードを忘れた」からの再設定です。**ログイン済みで自分から変更する画面はありません。** 運用者は `aws cognito-idp admin-set-user-password --permanent` でいつでも設定できます。
   - **「パスワードを忘れた」は、初回のサインインでパスワードを設定した後でないと、確認コードのメールが届きません。** 作成直後のユーザ（状態は `FORCE_CHANGE_PASSWORD`）では、画面は成功の形で応答しても、メールは送られません（実測。同じ設定で状態が `CONFIRMED` のユーザには届きます）。
   - **確認コードが届かないときは、次の順に試します。** (1) 作成直後なら、メールの一時パスワードでサインインし、そのまま新しいパスワードを設定します。メールを使いません。(2) 運用者が `aws cognito-idp admin-set-user-password --permanent` で直接設定します。(3) それでも届かないときだけ、迷惑メールのフォルダと、メールシステム側の隔離を確かめます。Cognito の既定の送信元は `verificationemail.com` ドメインです。
5. **ユーザの削除・無効化**: `aws cognito-idp admin-delete-user` / `admin-disable-user`。**すでに発行された ID トークンは、有効期限（最大 1 日）まで使えます。** 即時に締め出す場合は、`auth_mode` を切り替えてください。
6. **セッション**: ID トークンの有効期限は 1 日です。切れた後、開いたままのタブの API は 401 になります。ページを再読み込みするとサインインへ移ります。
7. **Basic に戻す**: `auth_mode = "basic"`（または削除）にして apply します。**Cognito のユーザープールとユーザは破棄されます。** `basic-auth` の SSM の値はそのまま使えます（[setup.md](setup.md) の「認証の準備」の `basic` の場合）。
8. **料金**: 新規のユーザープール（Lite）は 10,000 MAU まで無料です（2026-10-05 時点の公式の料金表）。メールは Cognito の既定の送信を使います。送信数に上限がありますが、管理者が数人の規模では問題になりません。apply の後、コンソールでプールの機能プランが Lite であることを確かめてください。
9. **認証なしのリクエストの見え方**: `cognito` では、画面は 302（Cognito の `/oauth2/authorize` へ）、`/api/` は 401（`WWW-Authenticate` なし）になります。200 が返ったら認証が働いていません。
10. **実行者の記録**: 申請の作成者と反映者が、申請履歴に出ます。`cognito` では Cognito のユーザ名（と、画面に出さない `sub`）、`basic` では Basic 認証のユーザ名だけです（単一の資格情報なので、複数人は区別できません）。実行者の記録を始める前の申請は「—」です。Lambda@Edge がサインイン済みのリクエストにだけ `x-rolust-actor` を付け、ビューアが送った同名のヘッダーは捨てます。
11. **ログアウト**: 画面右上の「ログアウト」で、Rolust の Cookie（`__Host-rolust-id`）を消し、Cognito のセッションを終えます。ログアウト後は Cognito のサインイン画面に戻ります。**ログアウトは発行済みの ID トークンを無効化しません。** コピーされたトークンは、有効期限（最大 1 日）まで使えます（受容した残余リスク）。即時に締め出すなら `auth_mode` を切り替えてください。ユーザの無効化や削除は、発行済みの ID トークンを止めません（上の 5）。`basic` にはログアウトがありません。

## 管理者の権限

`auth_mode = "cognito"` では、管理者の権限を Cognito のグループで 3 段階に分けます。階層で、**ユーザには最上位の 1 つだけを割り当てます**（複数に属しても、最上位が効きます）。

| グループ | できること |
|---|---|
| `viewer` | 参照だけ（マトリクス・申請履歴・差分確認の表示・信頼ポリシーの乖離の確認） |
| `editor` | 参照に加え、マトリクスの編集・ユーザとロールの登録・編集・削除・申請の作成と破棄・乖離を直す操作（「IAM を記録に合わせる（申請を作成）」「記録を IAM に合わせる」。申請の反映は `applier`） |
| `applier` | 作成に加え、信頼ポリシーの反映 |

- **申請者と反映者を分ける仕組みはありません**（2026-10-24 追記）。階層は積み上げなので、`applier` は自分が作った申請を自分で反映できます。四つ目の承認者を要求する運用（いわゆる 4 eyes）が要るなら、`editor` と `applier` を別の人に割り当て、`applier` にはマトリクスを編集させない、という運用で近づけるしかありません（Rolust 側に強制はありません）。
- **どのグループにも属さないユーザは、何もできません**（画面は「操作できる権限がありません」、API は 403）。ユーザを作ったら、グループを割り当てます。コンソールでもコマンドでも、結果は同じです。

  **AWS マネジメントコンソールで行う**

  > 画面の表記は日本語表示のものです。コンソールの更新で表記が変わることがあります。

  1. プール ID を控えます。`terraform -chdir=infra output -raw cognito_user_pool_id` で分かります。コンソールでは、Cognito のユーザープールの一覧から対象のプールを開くと、概要に表示されます。
  2. AWS マネジメントコンソールで Amazon Cognito を開き（リージョンは Rolust をデプロイしたリージョン）、「ユーザープール」から対象のプールを選びます。
  3. 左のメニューの「ユーザー管理」の「ユーザー」を開き、一覧から対象のユーザー名のリンクを開きます。
  4. 「グループメンバーシップ」の「ユーザーをグループに追加」を押します。グループの一覧（`viewer` / `editor` / `applier`）から、**最上位の 1 つだけ**をラジオボタンで選び、「追加」を押します。
  5. ユーザーの詳細の「グループメンバーシップ」に、選んだグループが出ていることを確かめます。
  6. 割り当てた後は、そのユーザが**再ログイン**します（グループは ID トークンに入るので、発行済みのトークンには入っていません）。

  **コマンドで行う**

  ```bash
  aws cognito-idp admin-add-user-to-group --user-pool-id <プール ID> --username <ユーザ名> --group-name applier --region <リージョン>
  # 外すとき: admin-remove-user-from-group
  ```

- **権限のグループを持たない版から更新するとき（既存の管理者がいる環境）は、`terraform apply` の直後に、現在の管理者へ `applier` を割り当てます。** グループができて割り当てるまでの間、その管理者は全 API が 403 になります。割り当てた後は、**再ログイン**が要ります（グループは ID トークンに入るので、発行済みのトークンには入っていません）。
- **権限の変更は、ID トークンの有効期限（最長 1 日）まで効きません。** グループから外しても、すでに発行されたトークンは期限まで元の権限で通ります。すぐに止めたいときは、ユーザを `admin-disable-user` しても、期限内のトークンは通ります（Lambda@Edge は署名と期限だけを検証します）。確実に止めるには `auth_mode` を切り替えてください（認証方式の選択の 5）。
- `basic` はグループを識別できないので、全権限です。
- **用語**: 「承認」の工程はありません。反映の権限を持つ人が「反映」を押します。申請履歴の「反映日」は、以前「承認日」と呼んでいたものです。
- **申請を渡す**: 画面 4 の各カードと申請履歴の各行に、申請の ID と「URL をコピー」があります。URL（`/requests?ids=<id>`）を開けば、差分確認と反映の画面が直接出ます。参照だけの人にも、差分は見えます（反映ボタンは無効です）。

## IP アドレス制限（任意）

Lambda@Edge は、Basic 認証（[setup.md](setup.md) の「認証の準備」の `basic` の場合）の前に、接続元の IP アドレスを SSM パラメータ `/rolust/ip-allowlist`（String）と照合します。**apply 直後の値は `0.0.0.0/0`（全許可）** で、Basic 認証だけの状態と挙動は変わりません。絞るときだけ、値を書き換えます。

書式は、IPv4 アドレスまたは CIDR をカンマ区切りで並べます（空白は無視されます）。CIDR を付けない IP アドレスは、その 1 つだけを許可します（`/32`）。IPv6 は扱えません。

```bash
# 展開先のルートで実行する
terraform -chdir=infra output -raw set_ip_allowlist_command    # 実行すべきコマンドを表示する

export MSYS_NO_PATHCONV=1                         # Git Bash で '/rolust/ip-allowlist' がパスに変換されるのを防ぐ
aws ssm put-parameter \
  --region us-east-1 \
  --name '/rolust/ip-allowlist' \
  --type String \
  --overwrite \
  --value '<許可する IP アドレスまたは CIDR>'
```

`--value` には、**自分が接続する回線の IP アドレス**（または CIDR）を入れます。カンマで複数並べられます。例: `203.0.113.0/24,198.51.100.7`（文書用のアドレスです。**そのまま実行しないでください**。実行すると、許可リストが文書用のアドレスだけになり、自分を含む全員が 403 になります）。

- 許可リストに含まれない IP からのアクセスは、SPA も `/api/*` も **403** になります。
- **値が空・書式不正・取得不能のときは、どのアクセスも通りません（`503`）。** 設定の誤りが、黙って制限を外さないためです。
- 変更が効くまで **最大 5 分**かかります（Basic 認証の資格情報と同じキャッシュです）。
- **自分を締め出したとき**: どの回線からでも `aws ssm put-parameter` で値を戻せます（SSM の API は、この IP 制限の対象外です）。戻してからも、効くまで最大 5 分は入れません。
- 使わないときは、初期値の `0.0.0.0/0` のままにしてください。

`--name` を既定値から変える場合は、Terraform の変数 `ip_allowlist_parameter_name` と `packages/edge-auth/src/index.ts` の `IP_ALLOWLIST_PARAMETER_NAME` を同じ値にして、再ビルドしてください。

## Basic 認証は「最小限のアクセス制限」である

（以下は `auth_mode = "basic"` のときの話です。`cognito` では、Basic 認証の位置に Cognito のサインインが入り、ユーザごとの資格情報になり、権限は Cognito のグループで分けます（下の「管理者の権限」）。発行済みの ID トークンは有効期限（最大 1 日）まで使えます。上の「認証方式の選択」を参照してください。）

このアクセス制限の要求は「認証なしで到達できない状態にする」ことです。Basic 認証は平文パスワードを毎リクエスト送るため（TLS 上ではあります）、加えて IP アドレス制限（上の「IP アドレス制限」）を選べます。SSO・WAF などの追加防御は行っていません。IP 制限と Basic 認証は CloudFront の側にあり、API Gateway の直 URL には効きません。直 URL は API キーで塞いでいます（下の「API Gateway のエンドポイントを配布しない」）。

### 総当たりへの対策は持たない（Issue #194 により 2026-10-23 追記）

**試行回数の制限・待ち時間の挿入・ロックアウト・試行の記録を、どれも持ちません。** 資格情報の照合は Lambda@Edge で行い（比較そのものは時間一定です）、誤った資格情報は何回でも試せます。失敗した試行はアプリケーションのログに残らず、CloudFront のアクセスログも取っていないため、総当たりを受けていることに気づく手段もありません。

したがって `auth_mode = "basic"` の防御は、次の 2 つに依存します。

- **資格情報を十分に長くすること。** Rolust は Basic 認証のパスワードに長さや文字種の制約をかけません（SSM に置いた値をそのまま使います）。推測も総当たりも成り立たない長さ——乱数で 32 文字以上——にしてください。利用者ごとの使い分けもできないため、1 つの資格情報が漏れれば全員分が漏れます。
- **絞れるなら IP アドレス制限を併用すること。** 上の「IP アドレス制限」の許可リストが、到達そのものを止める唯一の層です。

`cognito` では、連続した失敗に対する Cognito 自身の保護（規定回数を超えると待ち時間が入る挙動）が働き、パスワードは 12 文字以上かつ大文字・小文字・数字・記号を要求します。ただし、

- **多要素認証は無効**です（`mfa_configuration = "OFF"`。要るなら Terraform で有効にしてください）。
- ユーザープランは Lite のため、脅威保護（漏洩したパスワードの検出や適応型認証）は使えません。

管理者の資格情報が漏れた場合に到達を止める層は、`basic` と同じく IP 許可リストだけです。

強い保護が要る環境では、Rolust を自分のアカウントの既存の認証基盤の背後に置くか、IP 許可リストで絞ってください。

## API Gateway のエンドポイントを配布しない

**API Gateway のエンドポイントを配布しないでください。** CloudFront を経由しない経路であり、Basic 認証と IP 許可リストは効きません。CloudFront が付ける API キー（`x-api-key`）が無いリクエストは、API Gateway が Lambda を呼ぶ前に 403 で拒否します。API キーは多層防御の一層であり、認証の代わりではありません（`terraform -chdir=infra output api_gateway_invoke_url` にも同じ注記があります）。
