# 登録した IAM ロールの自動紐づけと、並び順の画面 2 への移設（Issue #135）

## 1. 目的と成功基準

ユーザプールをデプロイにつき固定の 1 つにした（Issue #108）ので、ロールをプールへ紐づけるかどうかを選ぶ意味が無くなった。登録した IAM ロールは無条件にプールへ紐づいた扱いにし、「ロールの紐づけ」機能を廃止する。列の並び順の変更は、IAM ロールの画面（画面 2）へ移す。

成功基準:

- ロールを登録しただけで、割り当てマトリクスにその列が出る。
- 画面 1 と画面 3 に「ロールの紐づけ」が無い。
- 画面 2 で並び順を変えて保存すると、マトリクスの列が同じ順になる。
- 信頼ポリシーにいる IAM ユーザの取り込み（Issue #80 の趣旨）は、登録時に引き継がれる。

## 2. 決定事項

| ID | 決定 | 根拠 |
|---|---|---|
| D-1 | 取り込みは登録時へ移す。信頼ポリシーを読めなければ、何も書かずに登録を拒否する（502） | #80 の趣旨を保つ。登録＝紐づけになるため。読めないときに拒否する慣行（旧 D-9）を引き継ぐ |
| D-2 | ロールの削除の拒否は「未反映の申請」だけ。紐づきを理由にした拒否は無くなる。削除時の確認に、残る割り当ての件数を出す | 外す操作が無くなるので、#79 の解除確認（GI-4）の置き換え |
| D-3 | `PoolRoleLink` は並び順（`position`）を持つ記録として残し、登録時に作り、削除時に消す。キーとアイテムの形は変えない | `listRoleLinks`・`isRoleLinked` の読み手（マトリクス・割り当て・申請作成）を変えずに済む。`position` を `IamRole` へ移す案は、読み手と既存データの移行を巻き込むので採らない |
| D-4 | 並び順は画面 2 の編集モード＋まとめて保存（`PUT /roles/order`） | 依頼者の選択（2026-10-07）。#103 の属性の編集モードと同じ型で、途中の状態が保存されない |
| D-5 | 既存の「登録済みだが紐づいていない」ロールは、実装前に本番を実測する。無ければ移行は不要。あれば、取り込みつきで紐づける移行スクリプトを足す | 人間が分岐付きで決めた事項。実測で確定した時点で発動する |
| D-6 | 画面 3 の empty は、画面 2 へ遷移する導線にする。画面 3 に登録モーダルは持ち込まない | 依頼者の承認（2026-10-07） |
| D-7 | 申請作成の除外理由 `not-linked` は廃止する。登録済みなら紐づいているので、`not-registered` に含まれる | 到達しない分岐を残さない |

## 3. 設計

### 3.1 登録（`POST /roles`）

検証は今のまま（書式 → 管理対象タグ）。続けて、書き込みの前に信頼ポリシーを読む（`iam:GetRole`。タグ条件つき。CRUD 系統の権限は既存で、IAM ポリシーは変えない）。別アカウントのロールは、ターゲット側の Reader を引き受けて読む（Issue #85 と同じ）。

書き込みの順序は、最後に IamRole を確定する:

1. 取り込む IamUser（未登録のもの。`attribute_not_exists`）
2. Assignment（`checked = reflected = true`。同じ値への書き直しなので冪等）
3. `PoolRoleLink`（`position` は、現在の最大 + 1。既にあれば `position` を保つ）
4. IamRole（`attribute_not_exists`。最後）

IamRole を最後にするので、途中で失敗しても「登録済みだが紐づいていない」状態は生まれない。残るのは、マトリクスに出ない孤児（登録の無いロールの交点と紐づけ）だけで、同じ登録のやり直しが続きから直す。孤児の紐づけは、IamRole を持たないのでマトリクスの列に出ない（既存の仕様: 列は登録済みのロールに絞る）。

失敗は 502（再試行可）。信頼ポリシーを読めない場合のコードと文言は、旧 `PUT /pool/roles` の GI-6 のものを移す。

### 3.2 削除（`DELETE /roles`）

未反映の申請（ロールロック）があれば 409。それ以外は、書き込みの順序を `PoolRoleLink` → 交点 → IamRole（最後）にする。`PoolRoleLink` を先に消すので、以後マトリクスの保存はそのロールの交点を作れない。AWS には触れない（FR-5.7）。途中の失敗は再試行可の 502 で、再実行で続きから片付く。

画面の確認に使うため、`GET /roles` の `RoleView` に割り当ての件数（反映済み・未反映）を足し、`linked` を外す。

### 3.3 並び順（`PUT /roles/order`）

本文は全登録ロールの ARN の配列。

- 登録されていない ARN は 400。重複は先頭を残す。
- 配列に無い登録済みロール（読んだ後に登録されたもの）は、現在の順で後ろに付ける。
- 順位が変わるロールだけ `position` を `attribute_exists` 付きで更新する（読んだ後に削除されたロールは飛ばす）。冪等で、途中の失敗は再保存で直る。

### 3.4 画面

画面案は Visual Companion で承認済み（`.superpowers/brainstorm/` の `screens-135-v1.html`。Git 管理外）。

- **画面 2 の一覧の並び**: 列順（`position` 順。紐づけを持たない登録済みロールは末尾にアカウント ID → ロール名の昇順）で返し、表示する。mockups.md 画面 2 の「ソートはアカウント ID → ロール名の昇順固定」を覆す（並び順を表の上で編集するため。承認済みの画面案の「順」列はこの並びを前提にしている）。ソート UI は置かない（NFR-1）。
- **画面 2**: 表の先頭に「順」列（一覧の位置 + 1）。ヘッダに「並び順を編集」（ロールが 2 件以上のときだけ）。編集モードは、行に「上へ」「下へ」（先頭の「上へ」と末尾の「下へ」は無効）、操作が「キャンセル」「保存（n 件）」に変わる。編集中は、登録・説明と色の編集・削除を無効にする。変更があるときの閉じ経路には破棄確認（GI-4）。フォーカスと読み上げは #100 の規則（`aria-live="polite"` で「<ロール名> を n 番目に移動しました」）を表の行に移す。
- **画面 2 の削除の確認**: 割り当てが残るときは `Alert`（warning）で件数を出し、フッターを「キャンセル」「割り当てごと削除」にする。未反映の申請があるときは、これまでどおり「削除できません」。
- **画面 2 の登録の成功通知**: 取り込んだ IAM ユーザの件数（うち新規）を添える。
- **画面 1・3**: 「ロールの紐づけ」と `onLinkRoles` を外す。画面 3 の empty は「IAM ロールが登録されていません」と、画面 2 への導線にする。

### 3.5 廃止するもの

`GET /pool/roles`・`PUT /pool/roles`、`LinkRolesModal`、`unlink-blockers`、`PoolRoleOption`・`UnlinkBlocker`・`SavePoolRolesResponse`、`RoleView.linked`、`not-linked`（D-7）。`role-import.ts` は登録から使う。

### 3.6 IAM・FR-5.7

IAM ポリシーは変えない（CRUD 系統は、タグ条件つきの `iam:GetRole` を既に持つ）。FR-5.7 の例外は、「ロールの紐づけ」から「ロールの登録」に移る。登録は、すでに `iam:ListRoleTags` で例外であり、`GetRole` を足しても範囲は広がらない（呼ぶのは登録の中だけ）。

## 4. テスト

- アプリコード（`packages/`）は TDD で書く。
- ユニット: 登録の書き込み順序と、途中失敗後の再実行、信頼ポリシーを読めない場合の無書き込み、削除の順序と拒否の条件、並び順 API の検証（未登録の ARN・配列に無いロール・削除済みロール）、画面 2 の編集モード（並べ替え・破棄確認・保存・無効化）。
- モックは、外部が拒否する状態を受理しうる。登録時の `GetRole`（タグ条件・別アカウント）は、統合テストか実測で確かめる。新規作成した検証用ロールを使い、既存ロールは書き換えない。実測後は、DynamoDB の登録と IAM ロールを片付ける。
- 実 AWS を要する成功指標に触れるので、依頼者が実測を引き取れる手順書を残す。
- 移行（D-5）が要る場合は、dry-run を既定にする。
