# IAM ユーザの CSV 一括登録（属性つき） — 設計

- 日付: 2026-10-04
- Issue: #98
- ブランチ: `feat/98-csv-bulk-register`
- 状態: spec レビュー待ち

## 1. 背景と目的

ユーザプールに IAM ユーザを追加するモーダル（`AddUsersModal`）は、アカウント ID 1 件とユーザ名の並びだけを受け取る。属性（Issue #61）は登録後にユーザごとに入れるしかなく、属性つきで多数のユーザを入れるには 1 件ずつ編集することになる。

本 Issue では、テキストエリアに CSV を貼り付けるだけで、ユーザと属性を一括で登録できるようにする。#61 で「CSV の仕様は属性の形が固まってから決める」として切り出した分の回収である。

### 現状の確認（読んだ事実）

- `POST /pools/:poolId/users` は `{ accountId, userNames }` を受け取る（`packages/api/src/handlers/pools.ts`）。`readUserNameList` が前後の空白を除き、空行を捨て、重複を黙って 1 件にまとめる（`packages/api/src/http.ts`）。
- `addUsers`（`packages/api/src/repository/pool.ts`）は、ユーザ名の書式を全件検証してから、1 件ずつ `PutItem`（`attribute_not_exists(pk)`）する。登録済みなら上書きせず、既存のアイテムを返す（FR-1.4・D-13）。`BatchWriteItem` は IAM ポリシー設計の権限一覧に無いので使わない。Put するアイテムには `attributes` を持たせていない。
- 属性は列の安定 ID（`columnId`）で持ち、`normalizeUserAttributes(raw, columns)`（`packages/core/src/attribute.ts`）が値の規則（前後の空白を除く・0〜128 文字・制御文字不可・空は未設定）を検証する。列はプールごとに最大 10 列で、属性列モーダルでだけ定義する。
- `AddUsersModal` は `PoolsScreen.tsx` の中にあり、アカウント ID（直近の ID をプリフィル。Issue #60）とユーザ名のテキストエリアを持つ。

### 成功基準

1. `AddUsersModal` で「1 件ずつ」と「CSV」を切り替えられる。アカウント ID の欄は両方で共通。
2. CSV の 1 行目はヘッダで、`ユーザ名` 列が必須。ほかの列名は、そのプールの属性列の名前と一致する。列の順序は自由で、属性列は一部だけでもよい。
3. 引用符・カンマ・値の中の改行（RFC 4180）、BOM、CRLF と LF を扱う。値の前後の空白（全角を含む）は除く。空の値は未設定。
4. 不正（ユーザ名の書式・属性値の規則・プールに無い列名・列名の重複・ユーザ名の重複・行数の超過）が 1 つでもあれば、全体を拒否して何も書かない。エラーは行番号つきで画面に出る。
5. 登録済みのユーザの行は、属性を含めて触らない。結果に「登録 n 件・登録済みのため変更なし m 件」を出す。
6. 新規ユーザは、属性を同じ書き込みで保存する。登録の前後で Assignment・ChangeRequest・AWS 上の信頼ポリシーは変わらない。AWS を呼ばない。
7. 「1 件ずつ」の既存の挙動（ユーザ名の改行区切り、重複の黙ったまとめ、`POST /pools` の作成時登録）は変わらない。
8. 新しい IAM 権限・DynamoDB のテーブル設計・`infra/` は変えない。

## 2. 決定事項

| ID | 事項 | 決定 | 出所 |
|---|---|---|---|
| D-1 | アカウント ID | モーダルの入力欄を使う（CSV には列を持たない）。CSV は 1 つのアカウントのユーザと属性だけを扱う | 依頼者の選択（2026-10-04） |
| D-2 | 登録済みのユーザの行 | 属性を含めて触らずに読み飛ばし、結果に件数を出す | 依頼者の選択。FR-1.4（再登録で既存のアイテムを変えない）のまま |
| D-3 | 列の対応 | ヘッダ行の列名で対応づける。並び順では対応づけない | 導出: 列の追加・削除・並べ替えで並び順の対応は壊れる |
| D-4 | 未知の列名 | 拒否する（列は作らない） | 導出: 列の定義は属性列モーダルの流れ（上限 10 列・名前の規則・一意性の検証）が持つ。CSV から暗黙に作ると、その検証と二重になる |
| D-5 | 失敗の扱い | 1 行でも不正なら全体を拒否して何も書かない。行番号つきで返す | 導出: FR-1.9 の「規則違反は拒否して何も変えない」と同じ形。部分登録は、直し方の案内（どの行が済みか）を複雑にする |
| D-6 | ユーザ名の重複 | 同じユーザ名が複数行にあれば拒否する | 導出: 行ごとに属性が違うと、どれを採るかが曖昧になる。「1 件ずつ」モードの黙ったまとめとは別に扱う（そちらは属性が無いので無害） |
| D-7 | 区切り | カンマだけ。タブ区切り（表計算ソフトからの貼り付け）の自動判定はしない | YAGNI。必要になれば別 Issue |
| D-8 | 行数の上限 | 1 回あたり 500 行（定数 `CSV_IMPORT_MAX_ROWS`） | 導出: NFR-1 は小規模前提で、1 件ずつ Put する（`BatchWriteItem` を使えない）ため、Lambda の実行時間に余裕を持たせる。超えるときは分けて登録する |
| D-9 | 検証の場所 | クライアントとサーバーの両方。規則は core の純粋関数 1 つに置き、両方が使う | 導出: クライアントは行番号つきで即時に返す。サーバーは境界で再検証する（CLAUDE.md「システム境界で入力を検証する」） |
| D-10 | API | 既存の `POST /pools/:poolId/users` に、`users`（属性つきの行）を受け取る形を足す。`userNames` と `users` はどちらか一方 | 導出: エンドポイントを増やさず、既存の権限・ルーティング・アカウント ID の検証を使い回す |
| D-11 | 属性の書き込み | 新規ユーザは `attributes` を同じ `PutItem` に含める（`attribute_not_exists(pk)` の条件つき） | 導出: 既存ユーザには何も書かれず、読み出しと更新を分けないので競合しない |
| D-12 | 追加する ID | **FR-1.10**（CSV による属性つきの一括登録）。FR-1.4 には「CSV 登録でも同じ」を追記する | `CLAUDE.md`「追加は末尾」。FR-1.4 の要件文は覆さない |

## 3. 設計

### 3.1 core: CSV の解析と検証（`packages/core/src/user-csv.ts`、新規）

```ts
export const CSV_IMPORT_MAX_ROWS = 500;

export interface UserCsvRow {
  userName: string;
  /** 列名 → 値。空の値は含めない。 */
  attributes: Record<string, string>;
}

export interface UserCsvError {
  /** CSV 上の行番号（ヘッダ行が 1）。ヘッダ自体のエラーは 1。全体のエラー（行数の超過）は null。 */
  line: number | null;
  message: string;
}

export type UserCsvResult =
  | { ok: true; rows: UserCsvRow[] }
  | { ok: false; errors: UserCsvError[] };

export function parseUserCsv(text: string, attributeColumnNames: readonly string[]): UserCsvResult;
```

- BOM を除き、RFC 4180 のとおりに引用符・`""`・値の中の改行を解釈する。末尾の空行と、すべてが空の行は無視する（行番号は元のまま数える）。
- ヘッダ: `ユーザ名` 列が無ければエラー。列名は前後の空白を除いて照合する。`ユーザ名` でも属性列名でもない列名はエラー（D-4）。同じ列名が 2 つあればエラー。属性列の名前が `ユーザ名` と同じ場合は、`ユーザ名` をユーザ名列として扱う（属性列には対応づけない）。
- 各行: ユーザ名は前後の空白を除き、空・書式の誤りはエラー（書式は既存のユーザ名の検証 `assertIamName` と同じ規則。core にある検証を使い、無ければ core へ移す）。値は `normalizeAttributeValue` で検証する。列の数がヘッダと合わない行はエラー。
- ユーザ名が複数行にあれば、2 行目以降をエラー（「n 行目と重複しています」。D-6）。
- 行数が `CSV_IMPORT_MAX_ROWS` を超えたら、行ごとの検証の前に全体のエラー 1 件だけを返す。
- エラーは行番号の昇順で、最大 50 件まで返す（超えたときは「ほか n 件」を最後に足す）。画面が長くならないため。

### 3.2 API

`POST /pools/:poolId/users` の本文は、次のどちらか。

- 従来: `{ accountId, userNames }`（変更なし）
- 新: `{ accountId, users: [{ userName, attributes?: Record<string, string> }] }`（`attributes` は列名 → 値）

両方、または両方とも無いときは `ValidationError`。`users` のとき、サーバーは次を行う。

1. 行数（1 以上 `CSV_IMPORT_MAX_ROWS` 以下）、ユーザ名の書式と重複を検証する。
2. プールの現在の属性列で、列名を `columnId` に解決する。解決できない列名は `ValidationError`（`field: "users[i].attributes"`、メッセージに行の位置と列名）。値は `normalizeAttributeValue` で検証する。
3. 検証が全件通ってから、`addUsers` へ渡す。

応答は 201。従来の `users`（全員。登録済みは実際の値）に加え、`createdCount` と `skippedCount` を返す。`userNames` のときも同じ項目を返す（互換のため `users` は変えない）。

`addUsers` は、行ごとに `{ user, created }` を返せるようにし、`users` を渡す形では `attributes` を `PutItem` に含める（D-11）。`attributes` が空の行は、従来どおり項目を持たせない。`POST /pools`（作成時の登録）は `userNames` のまま。

### 3.3 web

- `AddUsersModal`（`PoolsScreen.tsx`）に、`SegmentedControl`（Cloudscape）で「1 件ずつ」「CSV」の切り替えを足す。アカウント ID の欄は共通。CSV を選ぶと、ユーザ名のテキストエリアの代わりに CSV のテキストエリアを出し、その下に形式の説明（ヘッダ行・列名はプールの属性列名と一致・例）を出す。例はプールの属性列名から組み立てる。
- 入力のたびに `parseUserCsv` で検証し、エラーは `FormField` の下に「n 行目: …」の一覧で出す（`aria-live`）。送信ボタンは、エラーが無く 1 行以上あるときだけ有効。
- 送信: `api.addUsers(poolId, { accountId, users })`。成功の通知は「IAM ユーザを n 件登録しました（登録済みのため変更なし m 件）」。サーバーが返したエラーは、既存と同じく送信エラーとして出す。
- GI-4: CSV の入力があれば `dirty`（閉じる前に確認）。モードを切り替えても、入力は残す。
- 属性列が 0 件のプールでも使える（ユーザ名だけの CSV）。

### 3.4 失敗と競合

- 書き込みの途中で DynamoDB が失敗したら、既存の `addUsers` と同じく、その時点までに書いたユーザは残り、エラーを返す（トランザクションではない）。再度の登録は、登録済みを読み飛ばす（D-2）ので、同じ CSV をそのまま再送できる。この性質を画面のエラーに添える。
- 検証と書き込みの間に属性列が変わった場合（列の削除・名前変更）は、サーバーの検証が現在の定義で行われるので、拒否される（`columnId` に解決できない）。
- IAM を呼ばない。新しい権限は要らない（`PutItem` は既存）。

## 6. 範囲外

- 既存ユーザの属性の更新（D-2）。表形式での編集は #103。
- 属性列の自動作成（D-4）。ファイルのアップロード（テキストエリアへの貼り付けだけ）。タブ区切りの自動判定（D-7）。
- アカウント ID の列（D-1）。複数アカウントの一括登録は、アカウントごとに繰り返す。
- 登録のドライラン・取り消し。
