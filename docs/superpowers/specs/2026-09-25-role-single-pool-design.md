# 1 つの IAM ロールを紐づけられるユーザプールを 1 つに限る — 設計

- 日付: 2026-09-25
- Issue: #35
- ブランチ: `claude/issue-35-5d1xk3`
- 状態: spec 承認済み（2026-09-25）

## 1. 背景と目的

### 問題

#19 でプールとロールの紐づけを入れ、正本はこれを多対多とした（`requirements.md` の Data Model の補足）。IamUser はプール内でだけ一意（`POOL#<poolId>` / `USER#<userArn>`）で、同じ ARN を複数のプールに登録できる。この 2 つが重なると、「U が R を引き受けられるか」という 1 つの事実がプールごとの Assignment 2 件に分かれ、片方のプールで反映した結果がもう片方のマトリクスに出ない（Issue #35 の再現手順）。P-2（誰がどのロールを引き受けられるか見えない）の解決が崩れる。

ユーザが重ならなければ矛盾しない。未反映の申請はロールごとに 1 件まで（FR-4.6）で、反映は凍結入力に名前がある ARN しか触らない（`packages/core/src/merge.ts` の規則 1）ため。穴は「同じ ARN が、同じロールを紐づけた複数のプールに入る」組み合わせだけである。

### 採る案（C 案。2026-09-25 に依頼者が選択）

- **不変条件**: 1 つのロールは高々 1 つのプールに紐づく。ARN はプール内で一意（今のキー設計のまま）。合わせると、(ユーザ ARN, ロール) の Assignment は常に高々 1 件になる。
- IAM ユーザの登録は今のまま（プールをまたいだ ARN の重複を許す）。
- 複数システムの利用者が使うロールは「共通」のようなプールに紐づけ、使う人をそのプールにも登録する。

採らなかった案（A: ARN を全体で一意にする、B: 重なるときだけ拒否する）とその理由は Issue #35 にある。

### 成功基準

1. 紐づけの保存（`PUT /pools/:poolId/settings`）で、ほかのプールに紐づくロールを紐づけようとすると 409 を返し、何も変えない。
2. 2 つのプールが同じロールを同時に紐づけても、成功するのは片方だけになる。
3. 編集モーダルで、ほかのプールに紐づくロールを「<プール名> に紐づけ済み」と添えた無効な行で出す。
4. 移行の後、2 つ以上のプールに紐づくロールが 0 件になる（デプロイ先で実測する）。移行で割り当てが残る紐づけを外さない。
5. IAM ポリシー（`infra/`）を変えない。

## 3. 設計

### 3.1 テーブル設計

**RoleLinkOwner（新規）**

| 属性 | 値 |
|---|---|
| `pk` | `ROLELINK#<roleArn>` |
| `sk` | `OWNER` |
| `itemType` | `RoleLinkOwner` |
| `roleArn`・`poolId`・`createdAt` | — |

**不変条件（書き込みの順序で守る）**: 紐づけ（`POOL#<poolId>` / `ROLE#<roleArn>`）があれば、そのロールの逆引きがあり、その `poolId` は紐づけのプールと一致する。逆の「逆引きがあるのに紐づけが無い」（孤児の逆引き）は、書き込みの途中の失敗で起こりうる。孤児はロックが強すぎる側への失敗で、不変条件は破らない（3.3 で片付ける）。

**アクセスパターン（`TABLE-DESIGN.md` の末尾に追加）**

| # | 用途 | 操作 |
|---|---|---|
| 15 | ロールの持ち主のプール | GetItem / BatchGetItem `pk = ROLELINK#<roleArn>`, `sk = OWNER` |
| 16 | 持ち主の取得・返却 | PutItem（`attribute_not_exists(pk) OR poolId = :poolId`）/ DeleteItem（`poolId = :poolId`） |

Scan は使わない。旧版のコードは `ROLELINK#` のパーティションを読まないので、コードを前の版へ戻しても見え方は変わらない（ただし戻した版では D-1 の検証が効かない）。

### 3.2 API

すべて CRUD 系統で、AWS は呼ばない。

**`GET /pools/:poolId/settings`**: `PoolRoleOption` に 1 つ足す。

```ts
interface PoolRoleOption extends IamRole {
  linked: boolean;
  unlinkBlocker: UnlinkBlocker | null;
  /** ほかのプールに紐づいているときだけ非 null（このプールでは選べない）。 */
  linkedElsewhere: { poolId: string; displayName: string | null } | null;
}
```

- 持ち主は、登録済みの全ロールの逆引きを BatchGetItem（100 件ずつ）で引く。表示名は `listPools()`（アクセスパターン 1）で引く。
- 持ち主がこのプールで紐づけが無い（孤児）は、`linked: false`・`linkedElsewhere: null`（選べる）とする。
- 持ち主が存在しないプール（#18 で削除されたなど）を指すときも `linkedElsewhere` に出す（`displayName: null`）。自動では外さない（削除の経路は #18 で決める）。

**`PUT /pools/:poolId/settings` の順序**（#19 spec 3.2 の手順を拡張する）

1. **入力の検証（400）**: 変えない。
2. **差分**: 変えない（`toAdd`・`toRemove`）。加えて、登録済みの全ロールの持ち主を引く。
3. **検証（409）**: 次の 2 つをまとめて判定し、1 件でもあれば**何も書かずに** `ConflictError` を返す。
   - 外す側: #19 D-2 の外せない理由（変えない）。
   - 足す側（新規）: 持ち主がほかのプールのロール。文言（GI-6）: 「DeployProd はユーザプール <プール名> に紐づいています。1 つのロールを紐づけられるユーザプールは 1 つだけです。<プール名> の編集で外してから紐づけるか、使う人を <プール名> に登録してください。」
4. **書き込み**（D-6）:
   1. **持ち主の取得**: `toAdd` の各ロールについて、`attribute_not_exists(pk) OR poolId = :me` の条件付き PutItem。条件で失敗したら（手順 3 の後に別のプールが先に取った）、このリクエストで取った持ち主を条件付き DeleteItem で返し、409 を返す（ほかは書いていない）。返すのに失敗したら `console.error` で記録する（孤児が残るだけ）。
   2. 表示名の更新（変えない）。
   3. 紐づけの追加（変えない）。
   4. 外すロールの紐づけと残骸の交点の削除（変えない）。続けて、外したロールの持ち主を `poolId = :me` の条件付き DeleteItem で返す。
   5. **孤児の片付け**: 持ち主がこのプールで、紐づけが無く、今回も紐づけないロールの持ち主を、同じ条件付き DeleteItem で返す。
   - 手順 4.2〜4.5 の途中の失敗は、今と同じく `StorageError`（502、再試行可）。
5. **応答（200）**: 変えない。

**変えない API**: マトリクス・割り当ての保存・申請の作成は、今の紐づけの検証（`isRoleLinked` など）のままでよい。紐づけがあれば持ち主はそのプールだから（3.1 の不変条件）。

### 3.3 途中の失敗と回復

| 失敗した箇所 | 残る状態 | 見え方と回復 |
|---|---|---|
| 4.1 の途中 | このプールの持ち主（孤児）が数件 | 409 の補償で返す。返せなければ孤児。このプールの編集では選べる行に、ほかのプールでは「<このプール> に紐づけ済み」の無効な行に見える。このプールで次に保存すると 4.5 で返る |
| 4.2〜4.3 の途中 | 足した持ち主の一部が紐づけ無し（孤児） | 502。画面は設定を読み直す（今の動き）。同じく次の保存で片付く、または紐づけ直せる |
| 4.4 の紐づけ削除の後、持ち主の返却の前 | 孤児 | 同上 |

どの失敗でも、紐づけがあるのに持ち主が無い状態・持ち主がほかのプールである状態は生まれない。

### 3.4 画面（画面 1 の編集モーダル、`packages/web/src/screens/EditPoolModal.tsx`）

- `isItemDisabled` を「`unlinkBlocker` がある、または `linkedElsewhere` がある」に広げる。
- 状態の列: `linkedElsewhere` があれば「<プール名> に紐づけ済み」（`poolLabel` で表示名、無ければ `poolId`）。
- 一括選択: 今は外せないロールを常に選択に戻している。加えて、`linkedElsewhere` のロールは常に選択から除く。
- 見出しの説明に「ほかのユーザプールに紐づいているロールは選べません」を足す。
- 409 の表示・入力の保持は今のまま（手順 3 の文言がモーダル内に出る）。

### 3.5 移行スクリプト

- 処理本体は `packages/api/src/migrations/role-link-owners.ts`、入口は #19 と同じ形（`npm run migrate:role-link-owners --workspace @rolust/api`、`-- --apply` で書き込み）。ストアは `dynamo-migration-store.ts` を拡張する。
- 前提の確認（D-8）: #19 の印の無いプールがあれば、何もせずに「先に `migrate:pool-role-links` を実行してください」と出して終える（終了コード 1）。
- ロールごとの分類（プールの紐づけを全件 Query して、ロール → 紐づけたプールの表を作る）:

| 分類 | 条件 | `--apply` での扱い |
|---|---|---|
| single | 紐づけたプールが 1 つ | 持ち主を書く（既に同じプールなら何もしない） |
| keep-one | 2 つ以上、割り当てが残るプールが 1 つ | ほかのプールの紐づけを残骸の交点ごと外し、残すプールを持ち主に書く |
| unlink-all | 2 つ以上、割り当てが残るプールが 0（D-4） | 全プールの紐づけを残骸の交点ごと外す。持ち主は書かない |
| conflict | 2 つ以上、割り当てが残るプールが 2 つ以上（D-3） | 手を付けない。ロールとプールを列挙する（終了コード 1） |

- 「割り当てが残る」の判定は #19 D-2 の外せない理由と同じ（`checked || reflected` の交点がある、またはそのロールのロールロックの申請がそのプールから作ったもの）。判定の関数はサービスと移行で共有する。
- 持ち主が既にあり、紐づけと違うプールを指すとき（D-6 からは起きないが、手で直した場合など）は conflict と同じく列挙して触らない。
- 書き込みの順序は D-6 と同じ（外す → 持ち主を書く）。途中で失敗したら止めて表示する。分類はその時点のデータから毎回出し直すので、再実行で続きから直る。
- dry-run（既定）: 分類ごとの件数と、keep-one・unlink-all・conflict のロールごとのプールと割り当ての件数を表示する。何も書かない。Issue #35 の「2 つ以上のプールに紐づくロールと、割り当てが残るプールの数」の実測はこの出力で行う。

### 3.6 テスト

アプリのコード（`packages/`）は TDD。

- **api**:
  - リポジトリ: 持ち主の BatchGet（100 件ずつ）、条件付き Put（取れた / 同じプール / ほかのプール）、条件付き Delete（ほかのプールなら消さない）。
  - `GET .../settings`: `linkedElsewhere`（表示名、存在しないプール）、孤児は選べる行。
  - `PUT .../settings`: ほかのプールのロールで 409 かつ 1 件も書かない、外せない理由と両方あるときに両方の文言、4.1 の競合で 409 と補償、補償の失敗の記録、外したロールの持ち主の返却、孤児の片付け、書き込みの順序（持ち主 → 紐づけ、紐づけ → 持ち主）。
  - 移行: 前提の確認、4 分類、dry-run では書かない、2 回目は何もしない、途中の失敗で止まる、持ち主の食い違いの列挙。
- **web**: 無効な行と文言、一括選択で選ばれないこと。

モックは条件式を評価しないので、条件付き Put と Delete が実際に期待どおり通る・弾かれるかは 3.7 の実測で確かめる。

### 3.7 反映と実測（plan の最後のタスク）

このリポジトリのセッションの環境には AWS の認証情報も `terraform` も無いので、依頼者が実行する手順書として plan と PR に残す。terraform apply と本番データへの書き込みの前に、それぞれ依頼者の承認を得る。

1. README の手順で反映する（`npm run build` と terraform apply）。
2. **退避**: `aws dynamodb create-backup` を取る。移行前のプールごとの紐づけ（ロール ARN の集合）を記録する。
3. 移行を dry-run で実行し、分類ごとの件数を Issue #35 に記録する。conflict が 1 件以上なら止めて人が整理する（D-3）。
4. `--apply` → もう一度 dry-run（single だけ、keep-one・unlink-all・conflict が 0 件）の順に実行する。
5. **一致の確認**: 2 つ以上のプールに紐づくロールが 0 件。紐づけのあるロールはすべて持ち主が紐づけのプールと一致。割り当てが残る紐づけは手順 2 の記録から消えていない。
6. **画面での確認**: プール A に紐づくロールが、プール B の編集モーダルで「A に紐づけ済み」の無効な行になる。`PUT /pools/B/settings` で紐づけようとすると 409 で何も変わらない。A で外すと B で紐づけられる。
7. **片付けと一致の確認**: 手順 6 で変えた紐づけを元に戻し、手順 4 の後の状態と一致することを確かめる。

### 3.8 範囲の外と後続への申し送り

- 範囲の外: D-7（#44）、conflict のロールを自動で整理すること（D-3）。
- **#18（プールの削除）への申し送り**: プールを削除するときは、そのプールの紐づけと一緒に、そのプールを持ち主とする逆引き（紐づけのロールそれぞれの `ROLELINK#<roleArn>`、条件 `poolId = :poolId`）も消す。
- **#22（ロールの削除）への申し送り**: ロールの紐づけは持ち主のプール 1 つにしかないので、「全プールを Query して絞る」は逆引きの GetItem と持ち主のプールの操作で済む。ロールを削除するときは逆引きも消す。

**覆す**

- `requirements.md`
  - Data Model の補足「IamRole は UserPool に従属しない。1 つの IamRole は複数の UserPool に紐づけられ……多対多」: 従属しない点は保ち、1 つの IamRole を紐づけられる UserPool は高々 1 つ（1 対多）に改める。
  - FR-4.2 の定義の後の「当該 IamRole が属する UserPool の全 IamUser を採用しなかった」の理由（1 ロールが複数の UserPool から参照されうる）: 前提が変わったことを来歴付きで書き、採用した定義（全 IamUser の和集合）は保つ。保つ理由は、ほかのプールに登録された Rolust の IamUser を「管理外」と警告するのは誤りだから。
