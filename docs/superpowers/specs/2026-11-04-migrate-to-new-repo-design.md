- 日付: 2026-11-04
- Issue: #182（親: #11「OSS 公開の準備」。公開準備 7）
- 状態: 承認済み（依頼者、2026-11-04。D-3・D-9 は提案のとおり承認）
- 前提: 公開準備 1〜6 と #194 は完了済み（#176〜#181・#194 が閉じている）。後続は #183（公開・Release・旧リポジトリのアーカイブ）

## 1. 目的

#11 で決めた方針（新規のリポジトリを作る。履歴・Issue・PR は持ち越さない。開発も移す）を実行する。公開は #183 で行い、この Issue の終わりは「**非公開の新リポジトリに、検査を通した木が入り、そこで開発を続けられる**」状態である。

方針の理由は、旧リポジトリを公開すると実値と作者メールが残るためである。2026-11-04 の実測で、次を確かめた。

- 全履歴（812 コミット）の作者メールは、すべて noreply 以外である。
- 起点なしの保護値検査が、過去のコミットに実値の形（アカウント ID・メール・IPv4）を検出する。
- Issue 124 件・PR 126 件は、本文・コメント・編集履歴に実値が混ざりうる量で、機械的な検査の対象外である。
- 履歴を書き換えても、PR の参照（`refs/pull/*`）と編集履歴は GitHub 側に残り、確実に消せない。

## 2. 目標・非目標・アンチゴール

**目標**

- 新リポジトリ `kazuki-kudo/rolust`（非公開）に、旧 main から `aidlc/` と `docs/superpowers/plans/` を除いた木を、**1 つの初回コミット**で入れる。
- 守る対象 5 種（CLAUDE.md「保護値」）が、木・履歴・作者表記・コミットメッセージのどれにも無いことを、機械的に確かめる。
- 持ち越す木から、持ち越さないもの（`aidlc/`・旧 plan・旧コミット）への参照切れを、判断済みの方法で解消する。
- 旧リポジトリの Issue・PR の番号と、新リポジトリの番号が衝突しないようにする。
- 新しい作業ディレクトリで開発を続けられる（フック・gitleaks・メモリ）。

**非目標**

- 公開、Release、旧リポジトリのアーカイブ（#183）。
- CI/CD の再設計（#181 で完了。CD は持たない）。
- 文書に残る旧番号（約 3,000 箇所）の書き換え。注記で扱う（§6）。
- ライセンス・README の内容の変更。

**アンチゴール（技術的に動いても失敗）**

- 旧履歴・`aidlc/`・旧 plan が新リポジトリに 1 つでも入る。
- 実値（アカウント ID・CloudFront の DNS 名・自宅 IP・会社ドメイン・作者メール）が新リポジトリに入る。メモリや PR 本文からの持ち込みを含む。
- 旧チェックアウトから新リポジトリへ push してしまう（§4 の `origin` の付け替え漏れ）。
- 手順書を起こす過程で、実測の手順が欠ける、または実値が残る。

## 4. 順序

```
A. 旧リポジトリの PR（通常の流れ。両方の木で正しい変更だけ）
   └ 手順書と用語対応表を起こす／参照を付け替える
B. 木の書き出しと変換（ローカルの新しい空ディレクトリ。GitHub には何も作らない）
   ├ git ls-files から除外分を引いて書き出す
   ├ 新リポジトリ専用の変換を当てる（§5）
   └ 検査: 保護値（引数なし）・ci-local.sh・件数の照合 → すべて緑
C. 初回コミット（ローカル。作者は noreply）
   └ 全履歴（1 コミット）とメッセージの保護値検査 → 緑
D. GitHub（外から見える操作。1 手ごとに承認を得る）
   ├ 旧リポジトリを rolust-legacy に改名
   ├ 旧チェックアウトの origin を rolust-legacy に付け替え（直後に git ls-remote で確かめる）
   ├ 新リポジトリ kazuki-kudo/rolust を非公開で作り、C を push
   ├ 番号を予約（D-6）
   └ #183 に当たる Issue を新リポジトリに立て、#182 と #11 に結果を残す
E. 開発環境の移行（メモリ・フック・gitleaks）
```

- B・C で赤が出たら、旧リポジトリの名前は変わっていない。直して B からやり直す（D-2）。
- D の改名の**前**に、旧リポジトリの Issue（#182・#11・#183）へ書く記録を済ませる。改名後は `kazuki-kudo/rolust#182` が新リポジトリを指すため。
- A の PR は旧リポジトリで merge してから B に入る（B は merge 後の main から作る）。

`aidlc/` 以外の 63 ファイルが指す。次の方針で扱う。

- **spec 内**: 直さない。`docs/superpowers/README.md` の注記（「`aidlc/` は旧リポジトリの記録で、新リポジトリには無い」）で扱う。
- **直す箇所**（#182 が列挙したもの）: `docs/design/README.md` の「複写元」列・「凍結文書の所在」表・「凍結文書を正本に切り出す手順」、`CLAUDE.md` の「記録の場所」と「開発フロー」の凍結文書の項、`docs/development.md` の `aidlc` の行と 105・126 行、コードと CI と Terraform のコメント（`ci.yml`・`infra/backend.tf`・`infra/main.tf`・`infra/bootstrap/versions.tf`）、`eslint.config.js` の除外、`.gitignore` の OQ-4 のコメント、`.gitattributes` の `aidlc/** -text`。
- 直し方の原則: 「旧リポジトリの `aidlc/`（新リポジトリには持ち越していない）」と、**所在を保った文面**にする。参照を消して来歴を失わない。CLAUDE.md の訂正の規約（冒頭の追記注記と各箇所の来歴の二層）に従う。

### 5.4 旧コミットの SHA

履歴を持ち越さないので、旧リポジトリのコミットの SHA は新リポジトリで引けない。

- `.git-blame-ignore-revs`: 改行コードだけを変えたコミット 1 件（Issue #235）の SHA を持つ。新リポジトリでは引けないので、SHA の行を消してファイルは残す（`docs/development.md:106` が参照している。その文面は「新リポジトリには該当するコミットが無い」旨に直す）。
- `CLAUDE.md` の `09e9648`、`docs/design/README.md` の `2ce40d5`・`380af1b` など、文書中の SHA: 「旧リポジトリのコミット」と注記する。件数は B で `git grep` で取る（7〜40 桁の 16 進で、コミットを指す文脈のもの）。

## 6. 旧番号の扱い

- 文書中の「Issue #N」「PR #N」は書き換えない。
- `docs/design/README.md` と `docs/superpowers/README.md` に、「**番号が #{M} 以下のものは旧リポジトリ（`rolust-legacy`）のもの**」と 1 行書く（`{M}` は D-6 で数えた最大番号）。D-6 により、新リポジトリの番号は `{M}+1` から始まるので、この判定は機械的にできる。
- `CLAUDE.md` の「Issue #121」などの記述も同じ扱いとする。冒頭に同じ注記を置く。
- 新リポジトリの Issue・PR・コミットで旧番号を引用するときは「旧 #N」と書く。新リポジトリで `#N`（N ≤ M）を引くと「存在しない」になり、別物には当たらない。
- 作業中の私（Claude）へ: 文書の「Issue #N」を `gh issue view` で引く前に、N ≤ M か確かめる。N ≤ M なら旧リポジトリ（`--repo kazuki-kudo/rolust-legacy`）を引く。

## 7. 保護値の検査の切り替え（#177 から引き継いだ項目）

新リポジトリの木に当てる変換である（旧リポジトリでは `aidlc/` と plan があるので当てられない）。

- `.gitleaks-protected.toml` の `[allowlist] paths` から `aidlc/` と `docs/superpowers/plans/` を外し、旧リポジトリ向けの説明コメントを直す。
- `.github/scripts/protected-values-guard.sh` の `PROTECTED_BASE` の既定値を空にする。空のとき `history` は全履歴を走査する。`.github/scripts/protected-values-guard.test.sh` の、除外を確かめる 2 ケース（`aidlc/x.md`・`docs/superpowers/plans/p.md`）は、「除外されない（検出する）」ケースに反転する。起点が空のときの回帰ケースが無ければ足す。
- 作者メールの強制: `commit-msg` フックに、`git config user.email` が noreply 形式であることの検査を足す（D-5）。形式の検査は `protected-values-guard.sh text` を使い、同じルールで通す。
- #177 で据え置いた Minor 2 件を、最終検査の前に確かめる:
  - `history` は merge コミットだけで入った内容を見ない。新リポジトリの初回コミットは merge を含まないので、問題にならない見込み。確かめて、見送りの理由を CLAUDE.md の保護値の節に残す。
  - 許可したダミー値の直後に `_` 1 文字で続く実値を取り逃がす。初回コミットの木に対し、実際に該当が無いことを確かめる。
- 最終検査の入口は `./.github/scripts/protected-values-guard.sh`（引数なし）。ファイル名も同じルールで検査される。

## 8. 番号の予約（D-6）

- 新リポジトリを非公開で作り、C を push した後、**Issue を作る前**に行う。
- 切り出しの直前（A の merge 後）に、旧リポジトリの最大番号 `M` を `gh` で数える（Issue と PR は番号を共有する）。
- ダミーの Issue を `M` 件作って削除する。GraphQL の `deleteIssue` を使い、管理者権限が要る。削除しても番号は戻らず、欠番になる。
- GitHub の作成の目安（1 時間に約 500 件まで、数十件ずつ間隔を空ける）を守り、バッチで進める。途中で止まっても再開できるよう、作成済みの件数を毎回数え直す。
- 確かめ方: 予約の後に作る最初の Issue の番号が `M+1` であること。これを実測して、結果を #182 に残す。
- 公開の**前**にしかやらない（公開後は欠番が目立つ）。

## 9. 開発環境の移行（D-9）

- 新しい作業ディレクトリ（旧チェックアウトと別のパス）で、`git config core.hooksPath .githooks` を一度実行する。
- gitleaks 8.30.1 を PATH に入れる（CLAUDE.md の手順。Release の zip を取得し、SHA-256 を照合して展開する）。無いと検査もフックも終了コード 2 で止まる。
- Claude Code のメモリは、旧メモリから**選んで**持ち越す。
  - 実値（許可 IP など）は持ち越さない。
  - Issue・PR の番号に「旧」を付ける（§6 の判定は N ≤ M）。
  - 旧メモリは旧リポジトリ側に残す。
- 旧チェックアウトの `origin` を、改名の直後に `rolust-legacy` へ付け替える（アンチゴール）。

## 12. 前提・リスクと、builder に任せること

**リスク**

- 手順書の起こしで、実値の取りこぼし。→ 検査 2 と 6。
- 番号の予約が GitHub の作成の制限に当たる。→ バッチと間隔。途中再開を前提にする。
- 新リポジトリが非公開の間は、Actions の利用上限（旧リポジトリで 2026-10-24 に超過）の影響を受けうる。→ CI の確認は `ci-local.sh` を主とし、GitHub 上の実行は補助とする。

**builder に任せること（私の判断として、plan で詰める）**

- 手順書の節見出しの細かい整え方。
- 旧 SHA の注記の文面。
- 予約スクリプトの置き場所（リポジトリの外のスクラッチ領域とする。実行するだけで、成果物にしない）。
- ダミー Issue のタイトル・本文（実値なし。削除するので短くてよい）。
