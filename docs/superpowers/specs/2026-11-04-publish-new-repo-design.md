## 1. 目的と背景

非公開で作った新リポジトリ `kazuki-kudo/rolust`（初回コミット 1 件、Issue は #252 のみ、Actions の実行 0 件、タグ 0 件）を公開し、最初の Release を出し、旧リポジトリ `rolust-legacy` をアーカイブする。

想定する利用者は、公開後に GitHub で Rolust を見つけ、README を読み、**Release の tarball で自分の AWS に試しに入れる第三者**である（依頼者の言葉。2026-11-04）。

## 4. 手順の概要

順序が要る。各段階の GitHub への書き込みは、1 手ごとに依頼者の承認を得る。

**段階 A（非公開の間・読み取りと文書だけ）**
1. 公開前の最終確認: 木・履歴・Issue の本文の保護値検査（`protected-values-guard.sh all`・`text`）。Actions の実行 0 件、タグ 0 件、Releases 0 件、Issue は #252 のみであること。
2. 変更を作業ブランチ `chore/252-publish` にコミットする（push しても、トリガが `pull_request`・手動だけなので Actions は走らない。PR は作らない）。変更の内容は §6。

**段階 B（公開）**
3. 依頼者の承認を得て、リポジトリを公開に切り替える（取り消しにくい操作。公開後は fork やキャッシュで残りうる）。
4. 直ちに C-6 の設定（private vulnerability reporting、description、トピック）と C-3 の main の保護を入れる。

**段階 C（公開後）**
5. 作業ブランチを push して PR を出す。CI が走る。緑を確かめて merge（merge コミット）。
6. `main` の最新で CI を確かめ（C-2 により push で走る）、`## 未リリース` を `## v0.2.0 - 2026-11-04`（または実行日）に改める PR を出して merge する。
7. タグ `v0.2.0` を打って push する。`release.yml` が tarball を作って検査し、Release を作る。
8. **認証なしで取得できることを実測する**: `curl`（認証ヘッダなし）で tarball と `SHA256SUMS` を取得し、チェックサムを照合する。ブラウザでも Release のページから取得できることを確かめる。結果を `requirements.md` NFR-4・SM-2 に追記する。

**段階 D（片付け）**
9. 実機デプロイの Issue を新リポジトリに起票する（D-3）。
10. 旧リポジトリをアーカイブする。CI ロールの旧リポジトリ向けの信頼が残っていないかを確かめ、残っていれば外す（旧 #181 で `rolust-ci-plan` は削除済みの見込み。AWS を読む操作は、依頼者の SSO ログインが要る）。
11. 旧 #11 に結果をコメントして閉じる（C-9）。この Issue (#252) の「やること」に、D-3 による変更を反映する。

## 5. スコープ外

- 第三者の経路での実機デプロイ（D-3。別の Issue）。
- 新しい機能・不具合修正。
- Release の本文・tarball の構成の変更（`release.yml` は変えない）。
- 旧リポジトリの履歴の移し替え（旧 #182 で済み）。

## 8. 成功基準

1. リポジトリが公開で、private vulnerability reporting が有効であり、main の保護が入っている。
2. 非公開の間、Actions の実行が 0 件のまま公開に切り替えた（公開前後で `gh run list` を比べる）。
3. 公開リポジトリの最初の PR の CI が緑で、`main` へ merge 済み。
4. タグ `v0.2.0` の Release が作られ、本文の先頭に `CHANGELOG.md` の v0.2.0 の節がある。
5. 認証なし（`curl`・ブラウザ）で tarball と `SHA256SUMS` を取得でき、チェックサムが一致する。
6. 旧リポジトリがアーカイブされている。
7. 実機デプロイの Issue が起票され、旧 #11 が閉じている。
8. 公開した木・Issue・Release の本文に、保護値が無い（`protected-values-guard.sh all` と、Release の本文に対する `text`）。

## 9. リスク

- **公開は取り消しにくい。** 段階 B の前に、段階 A の確認をすべて通す。公開の切り替えは、依頼者が「公開してよい」と明示してから行う。
- 公開の直後から外の人が読める。`SECURITY.md` が約束する窓口（C-6）を最初に整える。
- 公開リポジトリの Actions のログは外から読める。CI は AWS の資格情報を持たない。ログに実値が出ないことは、最初の PR の CI の後に確かめる。
- Release の再作成は、公開後の外の人にとっては版の改ざんに見える。タグを打つ前に、段階 C の 6 までを済ませる。
