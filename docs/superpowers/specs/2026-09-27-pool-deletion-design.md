# ユーザプールを削除できるようにする — 設計

- 日付: 2026-09-27
- Issue: #18
- ブランチ: `feat/18-pool-deletion`
- 状態: spec レビュー待ち

## 1. 背景と目的

今の Rolust では、IAM ユーザは 1 人ずつ削除できる（`DELETE /pools/:poolId/users`、FR-1.5）が、ユーザプールそのものは削除できない。使わなくなったプールが一覧とマトリクスのプール選択に残り続ける。

Issue #18 は、2026-09-27 の追記で削除の条件を「配下の IAM ユーザと、割り当て可能な IAM ロールの紐づけが、どちらも空であること」に改めた。起票時の「配下の IamUser・Assignment を連鎖削除する」は取り下げた。空でないプールの削除は拒否し、先に IAM ユーザの削除と紐づけの解除を済ませてもらう。AWS 上の IAM ユーザ・IAM ロール・信頼ポリシーには触れない。

### 成功基準

1. IAM ユーザか IAM ロールの紐づけが 1 件でも残るプールの `DELETE /pools/:poolId` は 409 を返し、何も変えない。
2. 両方とも空のプールは削除され、一覧から消える。状態テーブルの `POOL#<poolId>` のパーティションに項目が残らない（デプロイ先で実測する）。
3. 削除したプールを持ち主とする孤児の持ち主（`ROLELINK#<roleArn>`）が解放され、そのロールをほかのプールで紐づけられる。
4. 削除したプールから作った申請が、申請履歴で「<識別子>（削除済み）」と表示される。反映済み・破棄済みの申請は消えず、凍結入力も変わらない（FR-4.5）。
5. 確認モーダルは、AWS 上の資源に触れないことを明記する。空でないプールでは、残っている IAM ユーザ数と IAM ロール数を削除できない理由として示す。
6. IAM ポリシー（`infra/`）を変えない。

## 2. 決定事項

| ID | 事項 | 決定 | 出所 |
|---|---|---|---|
| D-1 | 削除できる条件 | IAM ユーザ（`USER#`）と紐づけ（`ROLE#`）がどちらも 0 件。1 件でもあれば 409 で、何も書かない | Issue #18（2026-09-27 追記） |
| D-2 | 未反映の申請の扱い | 別途調べない。D-1 の 2 条件から、このプールから作った未反映の申請が無いことが導ける（3.1）。同時操作による競合で残る場合は受け入れる | 導出。競合は #48 の依頼者の判断（2026-09-26: 排他制御は要らない、競合は受け入れる）に従う。Issue #18 の推奨（未反映の申請があれば拒否）は D-1 で実質的に満たされる |
| D-3 | 削除の方式 | 物理削除して後片付けもする（A 案）。空であることを確かめる → 孤児の持ち主を解放する → 残った交点を消す → 最後に META を消す | 依頼者の選択（2026-09-27）。採らなかった B 案（論理削除: META に `deletedAt` を付けて一覧から外し、識別子の再利用を禁じる）は、META を読む処理すべてに分岐が要り、Issue の「META を削除する」から外れる |
| D-4 | 孤児の持ち主 | 持ち主がこのプールのロールを、条件付き DeleteItem（`poolId = :poolId`）で解放する | 導出: 放置すると、そのロールはほかのプールの編集画面で「<poolId> に紐づけ済み」の選べない行のまま戻らない。持ち主を取る条件が `attribute_not_exists(pk) OR poolId = :me` のため。#35 spec 3.8 からの引き継ぎ |
| D-5 | 残った交点 | このプールの Assignment を DeleteItem ですべて消す | 導出: IAM ユーザが空なら交点は通常残らない（ユーザの削除が連鎖削除する）が、競合（#48）で残りうる。残すと、同じ識別子でプールを作り直したときにそのまま出てくる |
| D-6 | 書き込みの順序 | 持ち主の解放 → 交点の削除 → META の削除。META を最後にする | 導出: 途中で失敗してもプールが残り、まだ空なので再実行で続きから片付く。META を先に消すと、失敗したときに API から片付ける手段が無くなる |
| D-7 | 識別子の再利用 | 許す。古いプールの申請は、同じ識別子の新しいプールの名前で履歴に出る。README の「制約と既知の帰結」に書く | D-3 の帰結（META を消すので `createPool` の `attribute_not_exists(pk)` が通る） |
| D-8 | 紐づけの数の渡し方 | `PoolView` に `linkedRoleCount: number` を足す。`GET /pools` でプールごとに `listRoleLinks` を 1 回呼ぶ | 導出: 確認モーダルで、残っている IAM ロールの数を削除前に出すため（Issue #18）。IAM ユーザの数は今の `users` から出せる |
| D-9 | 削除ボタンの見せ方 | 空でないプールでも無効にしない。モーダルで理由と直し方を示す | Issue #18（モーダルで理由を示す）。無効なボタンだけでは理由が分からない |
| D-10 | 履歴の「削除済み」の判定 | `poolNames` にキーが無いプールを削除済みとする。判定は `Object.hasOwn` で行う。API は変えない | 導出: `GET /change-requests` の `poolNames` は、今あるプールをすべてキーに持つ（表示名が無ければ値は `null`）。識別子の書式は `constructor` などを許すので、`in` 演算子では誤判定する |

## 3. 設計

### 3.1 未反映の申請が残らないことの導出（D-2）

IAM ユーザが空というだけでは言い切れない。#44 より前に削除したユーザを凍結入力に含む申請が残っている可能性があるためだ（`requirements.md` FR-4.2 の注記）。

紐づけも空であることを合わせると、言い切れる。

- 申請は、元のプールに紐づいたロールにしか作れない（`packages/api/src/services/change-request-service.ts` の `not-linked`）。
- 紐づけの解除は、このプールから作ったそのロールの未反映の申請があると拒否される（FR-1.7、`packages/api/src/services/unlink-blockers.ts`）。#19・#35 の移行で紐づけを外す場合も、同じ判定を使う。

したがって、紐づけが 0 件なら、このプールから作った未反映の申請は無い。例外は、判定と書き込みの間に同時操作が割り込む競合だけである。

### 3.2 API

**`DELETE /pools/:poolId`**（CRUD 系統。AWS は呼ばない）

処理本体は `packages/api/src/services/pool-delete-service.ts` の `deletePool(poolId)` に置く。ハンドラは `DELETE /pools/:poolId/users` と同じく薄くする。

1. **存在の確認**: `requirePool`。プールが無ければ 404。
2. **削除できるかの判定**: `listUsers`（アクセスパターン 2）と `listRoleLinks`（同 12）で数える。どちらかが 1 件以上なら **何も書かずに** `ConflictError`（409）を返す。文言は GI-6 に沿って、何が・なぜ・どう直すかを示す。両方残っていれば両方の文を入れる。
   > <プール名> を削除できません。IAM ユーザが 3 人登録されています。カードの「削除」で IAM ユーザを削除してください。IAM ロールが 2 件紐づいています。「編集」で紐づけを外してください。

   <プール名> は表示名があれば表示名、無ければ識別子。
3. **孤児の持ち主の解放**（D-4）: `listRoles`（同 5）→ `getRoleLinkOwners`（同 15。100 件ずつ）で、持ち主がこのプールのロールを見つける。それぞれを `releaseRoleLinkOwner`（同 16。条件 `poolId = :poolId`）で解放する。
4. **残った交点の削除**（D-5）: `listAssignments`（同 3）で出た交点を DeleteItem で消す。
5. **META の削除**（D-6）: `POOL#<poolId>` / `META` を DeleteItem で消す。
6. **応答（200）**: `{ poolId, releasedOwners, removedAssignments }`。件数は運用で確かめるときに使う。

手順 3〜5 の失敗は `StorageError`（502、再試行可）になる。

コア契約（`packages/core/src/api-contract.ts`）には、応答の型 `DeletePoolResponse` を足す。

**`GET /pools`**: `PoolView` に `linkedRoleCount: number` を足す（D-8）。`POST /pools` の応答では 0 を返す。

### 3.3 途中で失敗したとき・競合

| 失敗した箇所 | 残る状態 | 見え方と回復 |
|---|---|---|
| 3 の途中 | プールが残り、持ち主の一部が解放されない | 502。プールはまだ空なので、もう一度削除すれば続きから片付く |
| 4 の途中 | プールが残り、交点の一部が残る | 同上 |
| 5 | プールが残る（片付けは済んでいる） | 同上 |

競合（#48 の判断どおり受け入れる）:

- **判定と META の削除の間に、ほかの人がこのプールへロールを紐づける・ユーザを登録する**: 削除されたプールのパーティションに紐づけかユーザが残り、持ち主が削除済みのプールを指すことがある。そのロールは、ほかのプールの編集画面で「<識別子> に紐づけ済み」の選べない行になる。回復するには、運用者が `ROLELINK#<roleArn>` / `OWNER` を `aws dynamodb delete-item` で消す（手順は `TABLE-DESIGN.md` に書く）。同じ識別子でプールを作り直した場合は、そのプールの編集で紐づけを外しても直る。
- **判定の後に、このプールから作った未反映の申請が残る**（3.1 の例外）: その申請を反映すると、`markReflected` が削除済みのプールのパーティションに交点を作る。見えるのは、同じ識別子でプールを作り直したときだけである。

### 3.4 テーブル設計

キーは変えない。アクセスパターン 17 を末尾に足す。

| # | 用途 | 操作 | 要件 |
|---|---|---|---|
| 17 | プールの削除（Issue #18 により 2026-09-27 追記） | 存在の確認（GetItem META）→ 判定（#2・#12）→ 孤児の持ち主の解放（#5・#15・#16）→ 残った交点の削除（#3 ＋ DeleteItem）→ META の DeleteItem。すべて状態テーブル | FR-1.8 |

「ロールの持ち主」の節に、プールを削除するときは持ち主がそのプールのロールを解放すること、競合で残った持ち主は運用者が消すこと（キーの例つき）を足す。

### 3.6 テスト

アプリのコード（`packages/`）は TDD で書く。

- **api**
  - `deletePool`:
    - プールが無ければ 404
    - ユーザが残っていれば 409、ロールが残っていれば 409。両方残っていれば文言が両方入る。409 のときは 1 件も書かない
    - 持ち主がこのプールのロールだけを解放する（ほかのプールの持ち主と、持ち主の無いロールには触れない）
    - 残った交点を消す
    - META を最後に消す（順序も検証する）
    - 途中で失敗したら META を消さない
  - ハンドラ: `DELETE /pools/:poolId` のルーティング。`DELETE /pools/:poolId/users` と取り違えないこと。404・409・200 の応答
  - `GET /pools` の `linkedRoleCount`
- **web**
  - 確認モーダルの 2 つの状態。空でないときに「削除」ボタンが無いこと
  - 成功時の通知と一覧の読み直し。409 のときはモーダルが閉じず、文言が出ること
  - 履歴の 3 通りの表示。識別子が `constructor` の場合も含む
- **正本と README**: grep で、来歴の付け方と FR-1.8・アクセスパターン 17 の参照を確かめる

モックは条件式を評価しないので、条件付き DeleteItem が実際に期待どおり通る・弾かれるかは 3.7 の実測で確かめる。

### 3.7 反映と実測（plan の最後のタスク）

README の手順で反映する（`npm run build` → terraform apply。jump-admin / ap-northeast-1）。terraform apply の前に依頼者の承認を得る。実測は新しく作った検証用のプールだけで行い、既存の資源は書き換えない。

1. 検証用のプールを作ってユーザを 1 人入れ、どのプールにも紐づいていないロールを 1 つ紐づける。削除を試す → 409 になり、何も変わらない。
2. そのロールの申請を作り、申請履歴で破棄する（IAM は呼ばない）。
3. ユーザを削除し、紐づけを外してから削除する → 200 になる。
4. 一覧から消え、申請履歴でそのプールの申請が「<識別子>（削除済み）」と表示される。
5. 紐づけていたロールを、ほかのプールの編集画面で選べる（持ち主が解放されている）。
6. 状態テーブルに `pk = POOL#<識別子>` の項目が 0 件、`ROLELINK#<roleArn>` の持ち主が無い（`aws dynamodb query` と `get-item` で確かめる）。

実測で作った申請（破棄済み）は、FR-4.8 に沿って履歴に残す。手順 5 でほかのプールに紐づけを足したら、元に戻す。

### 3.8 範囲の外

- 空でないプールの連鎖削除（Issue #18 で取り下げ済み）。
- 論理削除と識別子の再利用の禁止（D-3 の B 案）。
- 競合への手当て（D-2、3.3。#48 の判断）。
