# 申請履歴の一覧を期間で絞って読む — 設計

Issue #116。申請履歴（画面 5）の一覧 API が、Query を最後まで辿らずに黙って欠ける欠陥を直し、件数が増えても初回表示と応答が肥大しないように、作成日の範囲で取得を絞る。

## 1. 目的と前提

- **目的**: (1) 申請履歴が 1 MB を超えたときに古い申請が黙って欠ける欠陥をなくす。(2) 画面の初期表示を直近 3 か月に絞り、件数が増えても応答と描画が肥大しないようにする。
- **決定済み**（依頼者との対話、2026-10-06）:
  - 今回は最小にする。GSI・カーソル式ページング・保持期間（TTL）は入れない。
  - 画面の既定の作成日の範囲は、今日から 3 か月前以降とする。
  - 下書き・失敗は、作成日の範囲にかかわらず常に返す（下書きは FR-4.6 のロックを握るため、期間外で見えなくなると新しい申請を作れない理由が画面から消える）。
- **実測**（本番、読み取りのみ、2026-10-06）: ChangeRequest は 26 件、テーブル全体で 12 KB、オンデマンド課金。1 件は約 0.5〜0.8 KB。2026-09-27〜10-05 の 9 日間で 26 件、増加は約 3 件/日（年 1,000 件前後）。
- **導出**（根拠つき。再質問しない）:
  - Query の 1 MB 上限に当たるのは約 1,500〜2,000 件（1.5〜2 年後）。Lambda・API Gateway の応答上限（約 6 MB）はさらに先。急ぎの性能問題ではないが、辿らない欠陥は上限を超えた時点で顕在化するので、先に直す。
  - ChangeRequest の `sk` は `CR#<uuid>` で作成日順ではない。期間で絞る Query には GSI が要るが、この規模では要らない。Query で全件を読み、API 内で絞る。DynamoDB の読み取り課金は読んだ量で決まるので、この絞り込みで課金は変わらない（今の規模では月に数円未満）。
  - Terraform・IAM は変えない（新しい AWS API を呼ばない）ので、`terraform apply` は要らない。Lambda（crud）と SPA の反映は README の手順による。
- **後続の Issue にする基準**: ChangeRequest が約 1,000 件、または一覧の応答が約 3 MB に達したら、GSI（`pk = CR`・`createdAt`）とカーソル式ページングを別 Issue で扱う。

## 2. 設計

### 2.1 リポジトリ（`listChangeRequests`）

- `queryAllWith`（`packages/api/src/ddb/client.ts`）で `LastEvaluatedKey` の最後まで辿る。これが欠けの修正。
- `queryAllWith` のコメント（移行スクリプト用・業務処理では使わない）を、業務処理でも使うように改める。1 MB を超えて取りこぼすと、履歴が欠けるため。
- 並びは従来どおり作成日の降順（コードで整列）。

### 2.2 サービスとハンドラ

- `GET /change-requests` が、クエリ文字列 `createdFrom`（ISO 8601 の日時、任意）を受ける。
- ハンドラで検証する。解釈できない値は `ValidationError`（400）。`createdFrom` は `Date` で解釈して UTC の ISO 文字列に正規化し、比較は `createdAt`（ISO 文字列）との辞書順で行う。
- サービス `listAllChangeRequests({ createdFrom })` は、次の申請を返す。
  - 状態が `draft` または `failed`: 常に返す。
  - それ以外（`applied`・`discarded`）: `createdAt >= createdFrom` のものだけ。
  - `createdFrom` が無ければ全件（従来どおり）。
- `createdTo` は API に持たせない。終端はクライアントが従来どおり画面側で絞る（取得量を減らす効果は始端で足りる）。

### 2.3 画面（画面 5）

- 作成日の日付範囲の**初期値**を「今日から 3 か月前〜（終端なし）」にする。終端が空の値は、既存の絞り込みが扱っている（`value.endDate || null`）。Cloudscape の `DateRangePicker` が終端の空を受けない場合は、実装時に実測し、受けないなら終端を今日にして `toDateRange` で空と同じに扱う。この判断は plan の実装で確かめる。
- 作成日の範囲の始端が変わるたび、`createdFrom`（ローカルの開始日 00:00:00.000 を ISO 化）を付けて再取得する。範囲を空にしたら `createdFrom` なしで再取得する（全期間）。
- 作成日の範囲は、**applied・discarded にだけ**画面側でも効かせる。draft・failed は範囲によらず表示する（API と同じ規則。絞りたいときは状態・対象ロールで絞る）。フィールドのラベルに「（下書き・失敗は対象外）」と添える。
- 「すべて解除」は、状態・反映日・対象ロールを空にし、作成日の範囲を**初期値（3 か月）に戻す**。ピッカー自身の「クリア」は全期間を意味する。`hasConditions` は、既定の範囲を条件と数えない（既定の状態で「表示 n / 全 m 件」を出さない）。
- 見出しの件数と内訳は「読み込んだ申請」の数になる。作成日の範囲の始端があるときは、見出しの下に 1 行で「作成日 YYYY-MM-DD 以降の申請（下書き・失敗は期間によらず）を表示しています」と出す。始端が無ければ出さない。
- 範囲の変更中は、既存の loading 状態（テーブルのスケルトン）を使う。再取得の失敗は既存のエラーパネル。
- 破棄・再読み込みの `reload` は、現在の範囲で再取得する。

### 2.4 テスト

- API（TDD）: Query が `LastEvaluatedKey` を辿ること（2 ページ目を返すモックで、全件が返る）。`createdFrom` の絞り込み（applied・discarded は境界を含む `>=`）、draft・failed は期間外でも返ること、`createdFrom` なしで全件、不正値で 400。
- 画面（TDD）: 初期の範囲が 3 か月前で、`createdFrom` を付けて取得すること。範囲を変えると再取得すること。範囲が draft・failed に効かないこと。「すべて解除」が範囲を初期値に戻すこと。見出しの注記の出し分け。
- 実測: Lambda（crud）を反映したあと、本番で `GET /change-requests?createdFrom=…` と無指定を叩き、件数が期待どおりであることを確かめる（認証は Cognito。検証専用ユーザ。既存の手順に従う）。1 MB の分割は本番に再現できないので、ユニットテストの 2 ページモックで担保する。
