# IAM ロールを削除できるようにする — 設計

- 日付: 2026-10-02
- Issue: #22
- ブランチ: `feat/22-role-deletion`
- 状態: spec レビュー待ち

## 1. 背景と目的

今の Rolust では、IAM ロールを登録（FR-2.1）して説明を編集（FR-2.3）できるが、登録を削除できない。使わなくなったロールが画面 2 の一覧と、ロールの紐づけのモーダルに残り続ける。

Issue #22 は #19・#35・#79・#85 より前に書かれた。起票時の範囲（全プールの Assignment の連鎖削除、信頼ポリシーの扱いの選択）は、その後に入った次の仕組みと重なる。

- 1 つのロールを紐づけられるユーザプールは高々 1 つ（#35。持ち主 `ROLELINK#<roleArn>`）。
- 紐づけの解除は、そのプールのそのロールの Assignment をすべて消し、**信頼ポリシーには触れずに**ロールを Rolust の管理外にする。そのプールから作った未反映の申請があれば拒否する（#79。FR-1.7）。
- 申請は、元のプールに紐づいたロールにしか作れない（`change-request-service.ts` の `not-linked`）。

このため依頼者は 2026-10-02 に、**紐づけを外してから削除する**形を選んだ（Issue の案 A。信頼ポリシーと AWS 上のロールには触れない）。#18 のプール削除（空にしてから削除する）と同じ形である。

### 成功基準

1. いずれかのユーザプールに紐づいているロール、または未反映（下書き・失敗）の申請があるロールの `DELETE /roles?arn=` は 409 を返し、何も変えない。
2. どちらも無いロールは削除され、画面 2 の一覧から消える。状態テーブルに `ROLE#<roleArn>`・`ROLELINK#<roleArn>`・このロールの交点が残らない（デプロイ先で実測する）。
3. AWS 上の IAM ロールと信頼ポリシーは変わらない（実測で前後を比べる）。削除は AWS を呼ばない（FR-5.7）。
4. 削除したロールの申請は申請履歴に残り、凍結入力も変わらない（FR-4.5）。
5. 確認モーダルは、削除できないときは理由と直し方（リンクつき）を示し、削除できるときは AWS に触れないことと、信頼ポリシーの principal を片付ける手順を示す。
6. IAM ポリシー（`infra/`）を変えない。
7. 画面 2 の登録モーダルの説明文とコメントの、#85 より前の記述（別アカウントのロールは差分確認・反映ができない）が直る（D-11）。

## 3. 設計

### 3.1 API

**`DELETE /roles?arn=<roleArn>`**（CRUD 系統。AWS は呼ばない）

処理本体は `packages/api/src/services/role-delete-service.ts` の `deleteRole(roleArn)` に置き、ハンドラ（`packages/api/src/handlers/roles.ts`）は薄くする。`arn` が無い・ロールの ARN でなければ 400。

1. **存在の確認**: `requireRole`。登録が無ければ 404。
2. **削除できるかの判定**（D-1・D-3・D-4）: ロールロック（`getRoleLock`。アクセスパターン 6 の 1 件版）と、持ち主（`getRoleLinkOwners`。同 15）を読む。持ち主があれば、そのプールの紐づけを `listRoleLinks`（同 12）で確かめる。この判定は `GET /roles` の `linkedPool` と同じ関数（`services/role-link-state.ts` の `readRoleLinkStates`）で行う。理由が 1 つでもあれば、**何も書かずに** `ConflictError`（409）を返す。文言は GI-6 に沿って、何が・なぜ・どう直すかを示し、両方あれば両方の文を入れる:
   > DeployProd を削除できません。ユーザプール「本番チーム」に紐づいています。そのユーザプールの「ロールの紐づけ」で外してください（信頼ポリシーは変わりません）。未反映の申請（下書き）があります。申請履歴で反映するか破棄してください。

   プール名は表示名があれば表示名、無ければ識別子（`listPools` で引く。紐づいているときだけ読む）。状態は「下書き」か「失敗」。
3. **孤児の持ち主の解放**（D-5 ①）: 手順 2 で持ち主があり紐づけが無かったときだけ、`releaseRoleLinkOwner(roleArn, <持ち主のプール>)`（同 16。条件 `poolId = :poolId`）で解放する。
4. **残った交点の削除**（D-5 ②）: `listPools`（同 1）で全プールを引き、プールごとに `listAssignments`（同 3）で出た交点のうち `roleArn` がこのロールのものを `deleteAssignment` で消す。`checked`・`reflected` を問わない。
5. **IamRole の削除**（D-6）: `pk = ROLE` / `sk = ROLE#<roleArn>` を DeleteItem で消す（`repository/role.ts` に `deleteRoleItem` を足す。サービスの `deleteRole` と名前が重ならないようにする。条件は付けない。手順 1 の後にほかの人が先に消していても、同じ結果になるため）。
6. **応答（200）**: `{ roleArn, releasedOwner: boolean, removedAssignments: number }`。件数は運用と実測で確かめるときに使う。

手順 3〜5 の失敗は `StorageError`（502、再試行可）になり、`console.error` に記録する。

コア契約（`packages/core/src/api-contract.ts`）に、応答の型 `DeleteRoleResponse` を足す。

**`GET /roles`**: `RoleView` に `linkedPool` を足す（D-8）。登録済みの全ロールの持ち主を `getRoleLinkOwners` で引き、持ち主のプールごとに `listRoleLinks`（同 12）で紐づけを確かめる。紐づけのあるロールだけ `linkedPool` を埋め、表示名は `listPools` から引く。持ち主が 1 件も無ければ、プールは読まない。`POST /roles` の応答（`IamRole`）は変えない。

### 3.2 途中で失敗したとき・競合

| 失敗した箇所 | 残る状態 | 見え方と回復 |
|---|---|---|
| 3 | ロールの登録と孤児の持ち主が残る | 502。ロールはまだ紐づいていないので、もう一度削除すれば続きから片付く |
| 4 の途中 | ロールの登録と交点の一部が残る | 同上 |
| 5 | ロールの登録が残る（片付けは済んでいる） | 同上 |

競合（#48 の判断どおり受け入れる）:

- **判定の後、IamRole の削除の前に、ほかの人がこのロールを紐づける**: IamRole の無い紐づけと持ち主が残る。マトリクスの列は登録済みのロールに絞るので（`handlers/matrix.ts`）、列には出ない。ロールの紐づけのモーダルにも出ないが、そのプールで次に保存すると、保存した集合に入らないので外れ、持ち主も返る（`pool-roles-service.ts` の手順 4.3）。同じ ARN を登録し直した場合は、そのプールに紐づいたロールとして見える。
- **判定の後に、このロールの申請が作られる**: 申請の作成は紐づけを要するので、上の競合がさらに重なったときだけ起きる。IamRole が消えた後なら、作成は `not-registered` で除外される。
- **持ち主が削除済みのプールを指し、そのプールに紐づけが残っている**（#18 の競合の残り）: 手順 2 は「<識別子> に紐づいています」で 409 を返す。直し方は `TABLE-DESIGN.md`「ロールの持ち主」の既存の手順（運用者が持ち主を消す。同じ識別子でプールを作り直して外しても直る）。

### 3.4 画面

**画面 2（IAM ロール管理、`packages/web/src/screens/RolesScreen.tsx`）**

- 一覧テーブルの右端に「操作」列を足し、行ごとに `Button variant="inline-link"` の「削除」を置く（`ariaLabel` は「<ロール名> を削除」）。削除できないロールでも無効にしない（D-9）。
- 確認モーダルは新しいファイル `packages/web/src/screens/DeleteRoleModal.tsx` に置く（`RolesScreen.tsx` が既に 446 行あり、`DeletePoolModal.tsx` と同じ形にする）。GI-4 に沿って `GuardedModal`（`dirty={false}`）を通す。
  - **削除できないとき**（`linkedPool !== null` または `unreflected !== null`）: 見出しは「IAM ロールを削除できません」。当てはまる理由ごとに直し方を示す。
    - 紐づき: 「ユーザプール「<プール名>」に紐づいています。そのユーザプールの「ロールの紐づけ」で外してください（信頼ポリシーは変わりません）。」に、そのプールを選んだマトリクス（`matrixPath(poolId)`。ツールバーから「ロールの紐づけ」を開ける）へのリンクを添える。
    - 未反映の申請: 「未反映の申請（下書き／失敗）があります。申請履歴で反映するか破棄してください。」に、その申請を強調した申請履歴（`historyPath(changeRequestId)`）へのリンクを添える。

    フッタは「閉じる」だけにする。
  - **削除できるとき**: 見出しは「IAM ロールを削除しますか」。本文には次の 3 点を書く。
    - <ロール名>（`<ARN>`）の登録を削除すること
    - **AWS 上の IAM ロールと信頼ポリシーには触れない**こと。Rolust が反映した IAM ユーザは信頼ポリシーに残り、外したいときは、削除の前にロールを紐づけ直し、割り当てマトリクスでチェックを外して申請・反映すること
    - 作成済みの申請は申請履歴に残ること。同じ ARN で登録し直せること

    ボタンは「キャンセル」と「削除」。処理中は GI-7 に沿って「削除中」と表示する。
  - **成功したとき**: モーダルを閉じて一覧を読み直し、「IAM ロール <ロール名> を削除しました」と通知する（GI-5）。
  - **404・409・502 のとき**: プールの削除と同じく、モーダルを閉じずに中にエラーを出す。一覧を読んだ後に状態が変わった場合は、409 の文言が理由を伝える。
- 登録モーダルのアカウント ID 欄の説明を「デプロイ先と異なるアカウントのロールも登録できます。ターゲットアカウント側の準備は README の「クロスアカウント構成」にあります。」に改める（D-11）。画面の冒頭のコメントも、別アカウントのロールは登録時にターゲット側の Reader を引き受けて検証し、差分確認・反映もできる、に改める。
- `packages/web/src/api-client.ts` に `deleteRole(arn)` を足す。

**画面 3（マトリクス）・画面 5（申請履歴）**: 変えない（D-10、3.2）。

### 3.5 テスト

アプリのコード（`packages/`）は TDD で書く。

- **api**
  - `deleteRole`:
    - 登録が無ければ 404
    - 紐づいていれば 409（文言にプールの表示名が入る。表示名が無ければ識別子）。ロールロックがあれば 409（下書き・失敗で文言が変わる）。両方あれば文言が両方入る。409 のときは 1 件も書かない
    - 孤児の持ち主（持ち主があり、そのプールに紐づけが無い）は紐づいていないとみなし、解放する。持ち主が無ければ解放しない
    - 複数のプールにまたがって、このロールの交点だけを消す（ほかのロールの交点には触れない）。`checked`・`reflected` を問わない
    - IamRole を最後に消す（順序も検証する）。途中で失敗したら IamRole を消さず、502 にする
    - 応答の `releasedOwner`・`removedAssignments`
  - ハンドラ: `DELETE /roles?arn=` のルーティング（`PATCH /roles` と取り違えないこと）。`arn` が無い・不正なら 400。404・409・200 の応答
  - `GET /roles` の `linkedPool`: 持ち主と紐づけがある（表示名あり・なし）、孤児の持ち主、持ち主が無い、の 3 通り。持ち主が無ければプールを読まない
  - `repository/role.ts` の `deleteRoleItem`（キーと、条件を付けないこと）
  - `readRoleLinkStates`: 持ち主と紐づけがある、孤児の持ち主、持ち主が無い、の 3 通り。持ち主のプールごとに紐づけを 1 回だけ読む
- **web**
  - 行の「削除」でモーダルが開く
  - 削除できない状態（紐づき・未反映・両方）で「削除」ボタンが無く、リンク先が `matrixPath` と `historyPath` であること
  - 削除できる状態の文言（AWS に触れないこと、principal の片付け方）
  - 成功時の通知と一覧の読み直し。409 のときはモーダルが閉じず、文言が出ること
  - 登録モーダルのアカウント ID 欄の説明が新しい文言であること（D-11 の回帰テスト）
- **正本と README**: grep で、来歴の付け方と FR-2.4・アクセスパターン 21 の参照、「4 列」が残っていないことを確かめる

### 3.6 反映と実測（plan の最後のタスク）

README の手順で反映する（`npm run build` → terraform apply。jump-admin / ap-northeast-1）。**terraform apply の前に依頼者の承認を得る。** main の未反映分（f80139e の文言 1 行。#85 の後に未 apply）も同時に反映される。

実測は、承認を得て新しく作る検証用の IAM ロールと検証用のプールだけで行い、既存の資源は書き換えない。画面の操作はヘッドレスの Playwright で、Basic 認証は SSM（us-east-1）から取る。

1. **準備**: デプロイ先アカウントに、管理対象タグ（`rolust:managed = true`）を付けた検証用の IAM ロールを作る。信頼ポリシーを退避する（`aws iam get-role`）。Rolust に登録し、検証用のプールを作って IAM ユーザを 1 人入れ、ロールを紐づける。
2. **紐づいているときの拒否**: 画面 2 で「削除」を開き、紐づきの理由とリンクが出ること、API が 409 を返して何も変わらないことを確かめる。
3. **未反映の申請があるときの拒否**: マトリクスでチェックを入れて申請（下書き）を作る。削除を試し、両方の理由が出ることを確かめる。申請履歴で破棄する（IAM は呼ばない）。
4. **残骸の注入**: 紐づけを外す。続けて `aws dynamodb put-item` で、解除が途中で失敗したときの残骸を作る。検証用のプールに、手順 1 の IAM ユーザとこのロールの交点（`checked = reflected = true`）を 1 件、孤児の持ち主（`ROLELINK#<roleArn>` / `OWNER`、`poolId` は検証用のプール）を 1 件書く。この時点でその IAM ユーザの削除が FR-1.5 で拒否されることを、API で確かめておく（掃除の効果を手順 7 で比べるため）。
5. **削除**: 画面 2 で削除する。200 が返り、`releasedOwner = true`・`removedAssignments` が注入した交点の数と一致すること、一覧から消え、成功の通知が出ることを確かめる。
6. **事後の確認**:
   - 状態テーブルに `ROLE#<roleArn>`・`ROLELINK#<roleArn>` が無く、検証用のプールにこのロールの交点が無い（`aws dynamodb get-item` と `query`）
   - 信頼ポリシーが手順 1 で退避したものと一致する（`Principal.AWS` の配列は整列してから比べる）
   - 手順 3 で破棄した申請が、申請履歴に「破棄」で残っている
7. **片付け**: 検証用のプールの IAM ユーザを削除する（手順 4 では拒否されたが、注入した交点が消えたので通る）。続けてプールを削除し、検証用の IAM ロールを AWS から削除する（`aws iam delete-role`）。破棄した申請は FR-4.8 に沿って履歴に残す。

### 3.7 範囲の外

- 紐づいたままのロールの削除（紐づけの解除を含む連鎖削除）。依頼者の選択で採らない（D-1）。
- 削除モーダルから信頼ポリシーの principal を片付ける申請を作ること（Issue の案 B）。既存の経路で行う（D-2）。
- AWS 上の IAM ロールの削除。Rolust の実行ロールは `iam:DeleteRole` を持たず、持たせない。
- 申請履歴の「削除済み」の表示（D-10）。
- 競合への手当て（3.2。#48 の判断）。
