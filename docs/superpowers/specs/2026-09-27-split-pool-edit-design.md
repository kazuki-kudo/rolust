# ユーザプールの編集を「名前を変更」と「ロールの紐づけ」に分ける — 設計

- 日付: 2026-09-27
- Issue: #46
- ブランチ: `feat/46-split-pool-edit`
- 状態: spec 承認済み（2026-09-27）
- 画面案: Design キャンバス「Rolust 表示名と紐づけの分割」（https://claude.ai/artifact/CM1feLkQ9Ecs6inZZNTFhu 、非公開）

## 1. 背景と目的

今の画面 1 の編集モーダル（`EditPoolModal`、Issue #17 / #19）は、表示名と割り当て可能な IAM ロールの紐づけを 1 つのモーダルで編集し、1 回の保存（`PUT /pools/:poolId/settings`）で両方を送る。

Issue #46 はこれを 2 つの画面に分けることを求める。依頼者に確かめた目的（2026-09-27）は **操作の頻度と性質の違い** である。表示名はめったに変えないが、ロールの紐づけは日常的に触る。紐づけの操作を軽くし、必要になった場面（多くは画面 3 のマトリクスで列の過不足に気づいたとき）からすぐ届くようにする。今は画面 3 から編集へ行けるのは、紐づけが 0 件のときの「このプールを編集」だけである。

### 成功基準

1. 画面 1 のカードから「名前を変更」と「ロールの紐づけ」を別々のモーダルで開ける。
2. 画面 3 では、プールを選んでいる間は常に「ロールの紐づけ」を開け、保存するとその場でマトリクスの列が変わる。
3. 名前の変更はロールの読み込み・検証（409）に左右されず、紐づけの保存は表示名に触れない。
4. FR-1.6・FR-1.7 の規則（表示名の検証、外せないロール、1 ロール 1 プール、持ち主の確保と返却）は変わらない。
5. IAM ポリシー・DynamoDB のテーブル設計・`infra/` を変えない。

## 2. 決定事項

| ID | 事項 | 決定 | 出所 |
|---|---|---|---|
| D-1 | 分ける目的 | 操作の頻度と性質の違い。紐づけを軽く、すぐ届く場所に置く | 依頼者の選択（2026-09-27。当初「保存の結合を切る」を選び、同日に改めた） |
| D-2 | 画面の形と入口 | どちらもモーダル。紐づけのモーダルは画面 1 のカードと画面 3 のツールバーの両方から開く。表示名は画面 1 のカードの「名前を変更」から開く | 依頼者の選択（2026-09-27）。専用ページは、マトリクスとの往復が生じるため採らなかった |
| D-3 | 紐づけの保存の仕方 | 今と同じく「保存」でまとめて送る。行ごとの即時保存は採らない | 依頼者の選択（2026-09-27、画面案の案 1 と案 2 を操作して比較）。今の検証（すべて検証してから書く）・一括選択・README の手順がそのまま使える |
| D-4 | API | 用途ごとに分ける。`PUT /pools/:poolId/display-name` と `GET` / `PUT /pools/:poolId/roles`。`PUT /pools/:poolId/settings` と `GET /pools/:poolId/settings` は廃止 | 依頼者の選択（2026-09-27）。Issue #17 / #19 の D-7 がまとめた理由（表示名だけ保存できた途中の状態）は、画面を分けると無くなる。呼び出し元は SPA だけで互換は要らない |

| D-6 | 画面の見た目 | Design キャンバスの「画面 1 ユーザプール（入口）」「名前を変更モーダル」「案 1 紐づけ：保存でまとめて」のとおり。見た目は Cloudscape に似せた近似で、実装は Cloudscape の部品の標準の描画に従う | 依頼者の承認（2026-09-27） |

Issue #17 / #19 の spec（`2026-09-25-pool-display-name-and-role-links-design.md`）の D-3（編集画面はモーダル 1 つで表示名と紐づけをまとめて保存）と D-7（保存の API は 1 つ）は、本 spec の D-2〜D-4 が覆す。spec は来歴の記録として書き換えない。

## 3. 設計

### 3.1 画面

**画面 1（ユーザプール）** — `packages/web/src/screens/PoolsScreen.tsx`

- カードのフッタは「このプールにユーザを登録」「名前を変更」「ロールの紐づけ」「削除」の順（`data-testid` は `rename-pool-<poolId>`・`link-roles-<poolId>`）。
- どちらのモーダルも、開いているプールを画面内の状態（`useState`）で持つ。`useRoute` による `edit` の読み取りは消す。

**名前を変更モーダル**（新規 `packages/web/src/screens/RenamePoolModal.tsx`）

- 見出しは「名前を変更」。表示名の `Input`（説明「空にすると識別子 `<poolId>` を表示します。1〜64 文字。」、placeholder は識別子）と、識別子（`Box variant="code"`、読み取り専用）だけを持つ。
- 初期値は一覧（`GET /pools`）で取得済みの `PoolView.displayName`。読み込みはしない（ロールの読み込みの失敗に左右されない。成功基準 3）。
- 検証は blur 時と送信時（GI-1）。`@rolust/core` の `normalizeDisplayName` を使う。
- `GuardedModal` を使い、入力が初期値から変わっていれば閉じ経路で破棄確認を挟む（GI-4）。
- 保存は `PUT /pools/:poolId/display-name`。保存中は「保存中」（GI-7）。成功ならモーダルを閉じ、一覧を読み直して「表示名を保存しました（<新しい表示ラベル>）」を通知する（`poolLabel`）。400・404・通信の失敗はモーダル内にエラーを出し、入力を保持する。

**ロールの紐づけモーダル**（`EditPoolModal.tsx` を `LinkRolesModal.tsx` に改名し、表示名の部分を抜く）

- 見出しは「ロールの紐づけ」、補助に「<表示ラベル>（`<poolId>`）」。
- 表（`selectionType="multi"`、`isItemDisabled`、列はロール名・AWS アカウント・状態）、外せない理由と「<プール名> に紐づけ済み」の出し方、一括選択の扱い、読み込み中のスピナー、読み込み失敗の `ErrorPanel` と再試行、ロール 0 件のときの画面 2 への導線、409（何も変えずに入力を保持）と 502・通信の失敗（エラーを出して読み直す）は、今の `EditPoolModal` のまま。
- `dirty` は選択の集合が読み込み時と違うこと。
- フッタの左に、変更があれば「未保存の変更 n 件（紐づけ a / 解除 r）」、無ければ「変更はありません」を出す（画面案の案 1）。
- 保存は `PUT /pools/:poolId/roles`。成功時の通知は呼び出し元が出す: 「<表示ラベル> のロールの紐づけを保存しました（紐づけ 追加 a 件 / 解除 r 件）」。

**画面 3（割り当てマトリクス）** — `packages/web/src/screens/MatrixScreen.tsx`・`packages/web/src/components/AssignmentMatrix.tsx`

- プールを選んでいる間は、ツールバーの「申請を作成」（primary）の左に「ロールの紐づけ」（`Button variant="normal"`、`data-testid="matrix-link-roles"`）を常に置き、`LinkRolesModal` をその場で開く。マトリクスの読み込み中・読み込み失敗でも開ける（モーダルは自分で読み込む）。
- 保存に成功したらモーダルを閉じ、通知を出してマトリクスを読み直す。申請対象の選択（列ヘッダのチェック）は触らない。外せるロールは割り当て（`checked` か `reflected`）が無く変更件数が 0 なので、もともと選択に入らない（FR-1.7 の解除の条件。plan 作成時の確認で、承認版の「新しい列に無いロールを選択から外す」を削った。2026-09-27）。読み直しの間に自動選択（DF-4）の基準を捨てると、再取得の後に変更のある列がすべて選択に戻るため、基準と選択の初期化はプールが替わったときだけにする（最終レビューで判明、2026-09-27。申請作成後の読み直しにも効く）。
- 紐づけが 0 件のときの「このプールを編集」（画面 1 への遷移）は「ロールの紐づけ」に改め、同じモーダルをその場で開く。`AssignmentMatrix` の `onEditPool` は `onLinkRoles` に改名する。

**`routes.ts`**: `poolEditPath` を消す。古い `/pools?edit=<poolId>` を開いても、一覧が表示されるだけになる。

### 3.2 API とサービス

すべて CRUD 系統で、AWS は呼ばない。API Gateway は `/api/{proxy+}` で受けるので `infra/` は変わらない。

| API | 変更 | 中身 |
|---|---|---|
| `PUT /pools/:poolId/display-name` | 新設 | 本文 `{ displayName: string \| null }`。文字列でも `null` でもなければ 400。`normalizeDisplayName` で正規化し、不正なら 400（`field: "displayName"`）。プールが無ければ 404（`requirePool`）、保存中に削除されたら 404（Issue #33 の挙動を引き継ぐ）。応答 200 `{ pool: UserPool }` |
| `GET /pools/:poolId/roles` | 改名（旧 `GET .../settings`） | 応答は `PoolRolesView`（旧 `PoolSettingsView`。中身は同じ: `pool` と登録済みの全ロールの `PoolRoleOption`） |
| `PUT /pools/:poolId/roles` | 新設（旧 `PUT .../settings` から表示名を抜いた） | 本文 `{ roleArns: string[] }`。入力の検証（400）→ 差分 → 外す側の検証とほかのプールが持つロールの検証（409、何も書かない）→ 持ち主の確保 → 紐づけの書き込み → 持ち主の返却、の順と、途中の失敗の 502 は今のまま。応答 200 `SavePoolRolesResponse`（旧 `SavePoolSettingsResponse`: `{ settings, added, removed }`） |
| `GET` / `PUT /pools/:poolId/settings` | 廃止 | ルートを消す（404） |

- `packages/api/src/services/pool-settings-service.ts` を `pool-roles-service.ts`（`getPoolRoles` / `savePoolRoles`）に改名し、表示名の正規化と更新を抜く。ほかのプールが持つロールの 409 の文言の「<プール名> の編集で外してから」は「<プール名> の「ロールの紐づけ」で外してから」に改める（画面の名前が変わるため。plan 作成時に追加、2026-09-27）。同じ理由で、割り当ての保存の 409（`packages/api/src/handlers/matrix.ts`）の「ユーザプールの編集で紐づけてから」を「「ロールの紐づけ」で紐づけてから」に、画面 2 の登録通知の「ユーザプールの編集で紐づけてください」を「ユーザプールの「ロールの紐づけ」で紐づけてください」に改める。
- 表示名の保存は `renamePool(poolId, displayName)` を新設する（置き場所は plan で既存のサービスの構成に合わせて決める）。`requirePool` と既存の `updateDisplayName` を使う。
- `@rolust/core` の `api-contract.ts` の型を改名し、`RenamePoolResponse`（`{ pool: UserPool }`）を足す。`packages/web/src/api-client.ts` は `renamePool`・`getPoolRoles`・`savePoolRoles` にする。
- 持ち主の確保と返却（Issue #35）はそのまま `PUT .../roles` に残る。README の「持ち主のユーザプールで何も変えずに保存すると、紐づけの無い持ち主が返される」手順は、ロールの紐づけモーダルで成り立つ。

### 3.3 テスト

アプリのコード（`packages/`）は TDD。

- **api**
  - `PUT .../display-name`: 本文の型の 400、表示名の検証の 400、プールが無いときと保存中に削除されたときの 404、成功時に紐づけと持ち主に触れないこと、`null` で解除できること。
  - `GET` / `PUT .../roles`: 今の settings のテストを移し、`PUT` が表示名に触れないことを足す。
  - `PUT .../settings` と `GET .../settings` が 404 になること。
- **web**
  - `RenamePoolModal`: 初期値、blur と送信時の検証、破棄確認、成功、400・404・通信の失敗で入力を保持すること。
  - `LinkRolesModal`: 今の `EditPoolModal.test.tsx` を移す（表示名の入力に関わるものは `RenamePoolModal` へ）。未保存の変更の件数の表示を足す。
  - 画面 1: 「名前を変更」と「ロールの紐づけ」がそれぞれのモーダルを開くこと、保存後の通知と読み直し。`?edit=` のテストは消す。
  - 画面 3: ツールバーの「ロールの紐づけ」と紐づけ 0 件の導線が、その場でモーダルを開くこと。保存後にマトリクスを読み直して通知を出すこと。

### 3.4 反映と実測（plan の最後のタスク）

モックでは確かめきれない点（本番の SPA とルーティング、ブラウザでの操作）を実測する。terraform apply の直前に依頼者の承認を得る。

1. README の手順で反映する（`npm run build` と terraform apply。変わるのは Lambda と SPA）。
2. 本番をヘッドレスの Playwright で操作する（Basic 認証は SSM から取る）。本番は依頼者も同時に触るため、既存のプールの表示名は変えない。
3. **退避**: 実測で紐づけを変えるプールについて、紐づけの集合（`GET .../roles` の `linked`）を記録する。
4. **確かめること**
   - 実測用のプールを作り、「名前を変更」で表示名を付けて外せること（成功後、画面 1 の見出しと画面 3 のプール選択に反映される）。
   - 画面 1 と画面 3 の両方から「ロールの紐づけ」を開けること。
   - 割り当ての残るロールを外して保存すると 409 になり、何も変わらないこと。
   - 画面 3 で紐づけを変えて保存すると、その場で列が変わること（どのプールにも紐づいていないロールがあれば実測用のプールで行う。無ければ手順 3 で記録したプールで、割り当ての無いロールを外して戻す）。
   - `PUT /api/pools/<poolId>/settings` が 404 になること。
5. **復元と一致の確認**: 変えた紐づけを元に戻し、手順 3 の記録と一致することを確かめる。実測用のプールは紐づけを外してから削除する（FR-1.8）。

### 3.5 範囲の外

- 紐づけの行ごとの即時保存（D-3 で採らなかった）。
- 紐づけの専用ページ・表の絞り込み。
- カードへの紐づけ件数の表示、プール作成時の表示名の入力。
