補足:

- **プール識別子** は原記述（`[idea]`）にも回答にも記述がない。FR-1.3（複数プールの作成）を成立させるには各プールを区別する手段が必要であるため導出した。 [derived] （Issue #108 により 2026-10-05: UserPool を固定の 1 つにしたので、識別子はデプロイごとの固定値（`ROLUST_POOL_ID`）になり、利用者は入力しない。DynamoDB のキーと ChangeRequest の `poolId` に残る）
- **IamUser の「所属 UserPool」属性** も回答文に直接の記述はない。FR-1.3 が複数プールを許し FR-3.1 が「選択された UserPool について」マトリクスを描く以上、IamUser がどのプールに属するかを保持しなければ両要件が成立しないため導出した。 [derived] （Issue #108 により 2026-10-05: プールが 1 つになったので、所属は固定プールで一意に決まる。属性とキーは残る）
- **AWSアカウントID の所在**: Q10=`B` により、AWSアカウントID は UserPool ではなく IamUser が持つ。1 つの UserPool に異なるアカウント ID の IamUser が混在しうる。 [Q10][Q16]
- **IamRole の ARN** は、FR-1.2 の IamUser と同様に `arn:aws:iam::<accountId>:role/<roleName>` 形式で導出する。原記述（`[idea]`）は IAMユーザについてのみ「ARN でユニーク管理できます」と述べており、ロール側の導出規則には言及がない。 [derived]
- **IamRole は UserPool に従属しない。** IamRole は UserPool とは独立に登録され（FR-2.1）、どの UserPool にも紐づかないこともある。1 つの IamRole を紐づけられる UserPool は高々 1 つであり（1 対多。FR-1.7）、紐づけは UserPool 側が持つ（Issue #19 により 2026-09-25 訂正。訂正前は、FR-3.1 のマトリクスが登録済み IamRole の全件を列に取るとしていた）。高々 1 つに限るのは、同じ ARN の IamUser が同じ IamRole を紐づけた複数の UserPool に入ると、「その IamUser がその IamRole を引き受けられるか」という 1 つの事実が UserPool ごとの Assignment 2 件に分かれ、片方で反映した結果がもう片方のマトリクスに出ず、マトリクスが実態とずれるためである（Issue #35 により 2026-09-25 訂正。訂正前は「1 つの IamRole は複数の UserPool に紐づけられ、それぞれのマトリクスから参照されうる。紐づけは UserPool 側が持つ多対多の関係」としていた）。紐づけは列の並び順 `position` を持つ（FR-1.7。Issue #100 により 2026-10-04 追記）。 [idea][Q2] （Issue #108 により 2026-10-05: UserPool が 1 つになったので「高々 1 つ」の制約は外れた。紐づけ（FR-1.7）は残り、紐づけたロールがマトリクスの列になる。上の「高々 1 つ」の理由は、複数の UserPool があった時点のものである）（Issue #135 により 2026-10-07: 登録した IamRole は無条件に UserPool に紐づくので、「どの UserPool にも紐づかないこともある」はなくなった。紐づけの記録は、列の並び順 `position` を持つものとして残る。登録（FR-2.1）が作り、削除（FR-2.4）が消す）

### Assignment と ChangeRequest の関係

**両者は別の実体であり、同時に存在する。** [Q1][Q13][derived]

| | Assignment | ChangeRequest |
|---|---|---|
| 表すもの | **あるべき状態** — マトリクスの現在のチェック内容 | **凍結された変更イベント** — ある時点で反映しようとした事実 |
| 変化のしかた | 管理者のチェック操作のたびに随時変化する [Q2] | 作成時点の入力を凍結し、以後変化しない [Q18] |
| 生成契機 | チェック操作の保存 [Q2] | 管理者の明示的な「申請を作成」操作のみ [Q17] |
| 反映時に適用されるもの | — | **こちら**。凍結された入力を適用する [Q18] |

この分離により、**反映した内容と監査記録は必ず一致する**。反映処理はその時点の生の Assignment ではなく、下書き ChangeRequest に凍結された入力を適用するためである。 [Q18]

### 信頼ポリシーの扱い

**信頼ポリシー（TrustPolicy）は Rolust が保持する実体ではなく、AWS 上の IAMロールに属する外部状態として扱う。** Rolust は反映のたびに AWS から現在の信頼ポリシーを読み、ChangeRequest の凍結入力との差分を算出する。 [idea][Q3][Q7]

**信頼ポリシー全文のスナップショット（before / after）は保存しない。** Q13=`A` により ChangeRequest が保持するのは入力（対象ロール・追加/削除ユーザ）と反映結果までであり、差分の表示は保存された入力と AWS 上の現在の状態から都度再算出する。 [Q13]

**FR-2.1 の登録時検証**（Issue #26 により 2026-09-24 追記）: デプロイ先アカウントのロールを登録するとき、システムは `iam:ListRoleTags` で管理対象タグ（`<managed_tag_key>` = `<managed_tag_value>`、既定は `rolust:managed` = `true`）を検証し、ロールが存在しない（`NoSuchEntity`）・タグが無い・値が一致しない場合は 400 で登録を拒否する。実行ロールの権限不足は入力の誤りではないため 502 で返す。デプロイ先と異なるアカウント ID のロールも、ターゲット側の Reader を引き受けて同じ検証をする。ターゲット側のロールを引き受けられなければ 502 で拒否する（Issue #85 により 2026-09-30 訂正。訂正前は、`iam:ListRoleTags` が呼び出し元アカウントに対して解決され、別人の同名ロールを見てしまうため、別アカウントのロールは検証せずに受理した）。3.4 の RQ-4 = A と code-generation の質問 11 = A による（`packages/api/src/handlers/roles.ts`）。この検証は FR-5.7・C-4 を意図的に破る（FR-5.7 の注記）。

> **追記**（Issue #194 により 2026-10-24）: 登録は、**Rolust 自身の実行ロール**（`infra/main.tf` の `local.self_role_arns`。CRUD・Diff・Apply・Lambda@Edge の実行ロールと API Gateway のサービスロールの 5 本）を 400 で拒否する。拒否はタグ検証より前に行い、AWS も DynamoDB も呼ばない。照合はアカウント ID とロール名の対で行い、ロール名は大文字小文字を無視する（IAM は大小だけが違う 2 つのロールを作れない）。一覧は Lambda の環境変数 `ROLUST_SELF_ROLE_ARNS` として渡り、IAM ポリシーの `Sid: DenySelfEscalation` と同じ `local` を参照するので、両者が食い違うことはない。反映側の `DenySelfEscalation`（`iam-policy-design-note.md` 3.2）は管理対象タグが付いていても拒否するが、それだけだと違反が操作の連鎖の末尾（反映）で初めて現れるため、登録の時点でも返す。

**FR-2.2 とクロスアカウント構成**（Issue #26 により 2026-09-24 追記。Issue #85 により 2026-09-30 訂正）: 別アカウントのロールも、デプロイ先アカウントのロールと同じ手順で、登録・紐づけ・差分確認・反映ができる。Rolust の Lambda が、ターゲットアカウントに作った 2 つのロール（CloudFormation テンプレート `cloudformation/target-roles.yaml` で作る。Issue #92 により 2026-10-13 訂正。訂正前は手動で作るとしていた）を AssumeRole して、IAM を呼ぶ（`docs/design/iam-policy-design-note.md` 3.3。`packages/api/src/aws/iam-client.ts`）。読み取り（登録時のタグ検証の `iam:ListRoleTags`、紐づけ時と差分確認の `iam:GetRole`）は `RolustTrustPolicyReader`（CRUD・Diff が引き受ける）、更新（`iam:GetRole`・`iam:UpdateAssumeRolePolicy`）は `RolustTrustPolicyManager`（Apply だけが引き受ける）で行う。CRUD が Manager を引き受けられないので、CRUD が AWS へ書き込まないという FR-3.2 の保証は、別アカウントでも保たれる。ロールの ARN のアカウント ID がデプロイ先（API Gateway の `requestContext.accountId`）と一致すれば、従来どおり実行ロール自身の資格情報を使う。一致しなければ、そのアカウントの Reader または Manager を引き受けた資格情報を使う。デプロイ先を判定できない場合は、どちらの資格情報を使うかを決められないので、IAM を呼ばず、差分確認では読み取りエラー、反映では状態「失敗」とする（エラーコード `DeployAccountUnknown`）。**引き受けに失敗しても、デプロイ先の資格情報で呼び直さない。** IAM の API は `RoleName` しか受け取らず、呼び出しに使った資格情報のアカウントに対して解決されるため、呼び直すと、デプロイ先に同名で管理対象タグの付いたロールがあった場合にそのロールの信頼ポリシーを読み書きして「反映済み」と記録し、監査記録の roleArn と実際に書き換えたロールが食い違う（§ Assignment と ChangeRequest の関係「反映した内容と監査記録は必ず一致する」を破る。Issue #27）。引き受けに失敗したときは、登録と紐づけを 502 で拒否し、差分確認では読み取りエラー、反映では状態「失敗」とする（文言は、何が・なぜ・どう直すかを含む。GI-6）。ターゲット側のロールは、`docs/guide/cross-account.md` の手順で（Issue #178 により 2026-10-18 訂正） CloudFormation テンプレート（`cloudformation/target-roles.yaml`）により作る（Terraform の対象外。NFR-4 の注記。Issue #92 により 2026-10-13 訂正。訂正前は手動で作るとしていた）。訂正前は単一アカウント構成で、別アカウントのロールを登録できたが、差分確認と反映は IAM を呼ばずにエラーコード `CrossAccountRoleNotSupported` で失敗した（Issue #27。code-generation の質問 3 = A）。principal 側の IamUser は別アカウントでもよい。

**FR-4.2 の「Rolust が管理する principal」の定義** [derived]:

> Rolust に登録されている**全 IamUser の ARN 集合**（UserPool を横断した和集合）を「Rolust 管理下の principal」とする。信頼ポリシー中の principal のうち、この集合に含まれないものはすべて「Rolust 管理外」とする。

**反映処理での管理下の範囲**（Issue #26 により 2026-09-24 追記）: 上の定義は FR-4.2 の警告表示にだけ使う。反映処理（FR-5.1）での「Rolust 管理下の principal」は、**対象 ChangeRequest の凍結入力（追加・削除する IamUser）に名前が挙がっている ARN 集合**であり、反映時点の IamUser 集合は参照しない（code-generation の質問 5 = A、`packages/core/src/merge.ts` の規則 1、`packages/core/src/unmanaged.ts`）。削除済みの IamUser を凍結入力に含む申請について、FR-5.2（凍結入力どおりに適用）と FR-5.1（管理外を保全）が相反する結論を出すのを避けるためである。（Issue #44 により 2026-09-26 追記）FR-1.5 は、当該 UserPool から作った未反映の ChangeRequest の凍結入力に挙がっている IamUser の削除を拒否するようになった。この規則は変えない。削除済みの IamUser を凍結入力に含む未反映の申請は、Issue #44 より前に削除した場合と、判定と削除の間に申請が作られた場合にだけ残る。

**FR-3.2 の交点の保存の前提**（Issue #194 により 2026-10-24 追記）: 交点の保存（`PUT /api/pool/assignments`）は、対象の IamUser が当該 UserPool に登録済みであることを API が確かめ、無ければ 409 で拒否する（`packages/api/src/handlers/matrix.ts`）。交点はそのまま凍結入力になり（FR-4.5、`packages/core/src/matrix.ts` の `buildFrozenInput`）、反映で信頼ポリシーの principal になるため、登録を経ていない ARN がここから入ると、登録の入口（FR-1.1・FR-1.2）が行う検証——許可リスト（FR-1.11）と IAM の命名規則——を迂回できる。登録済みであることを確かめることで、この経路がその両方を継承する。紐づけの無いロールを拒否する既存の検証（FR-1.7）と対になる、操作の場での検証である。画面はプールに登録済みのユーザの行しか描かないので、画面の挙動は変わらない（`interaction-spec.md` は変えない）。

**プレースホルダは管理外に数えない**（Issue #16 により 2026-09-25 追記）: 警告表示と反映処理のどちらの範囲でも、プレースホルダ Statement（`Sid: RolustPlaceholder`。FR-5.1 の注記）の principal は管理外に数えない。Rolust 自身が挿入する Statement だからである（`packages/core/src/unmanaged.ts`）。数えると、プレースホルダの principal であるアカウント root（`arn:aws:iam::<account-id>:root`）が差分確認画面で管理外として警告される。

この定義は Q3=`C` が要求する「Rolust 管理外の principal を検出する」ための判定基準を本ステージで導出したものである。Q3 も Q9 も方針（保全する・警告する・管理者はデータモデルに含めない）を確定させただけで、算出方式そのものには言及していないため `[derived]` として扱い、承認ゲートで確認する。

代替案として「当該ロールにチェック済みの IamUser のみを管理下とする」定義を検討したが、採用しなかった。その定義ではチェックを外した瞬間にユーザが「管理外」に転落し、保全方式（FR-5.1）によって信頼ポリシーから永久に削除できなくなるため、FR-5.1 の 2 つ目の受け入れ基準（変更業務）が成立しない。

また「当該 IamRole が属する UserPool の全 IamUser」という定義も採用しなかった。Data Model のとおり IamRole は UserPool に従属せず、1 つの IamRole が複数の UserPool から参照されうるため、「当該ロールが属する UserPool」が一意に定まらない。

（Issue #35 により 2026-09-25 追記）この理由の前提は変わった。Issue #35 で 1 つの IamRole を紐づけられる UserPool は高々 1 つになり（Data Model の補足）、「当該ロールが紐づく UserPool」は一意に定まる。それでも上の定義（全 IamUser の和集合）を保つ。IamUser はプールをまたいで同じ ARN を登録でき、ほかの UserPool に登録された Rolust の IamUser が手動などで信頼ポリシーに入っていることがある。「当該ロールが紐づく UserPool の全 IamUser」を管理下とすると、それらを「管理外」と警告することになり、Rolust に登録済みの principal を管理外と呼ぶのは誤りだからである。

**この定義の帰結**（Issue #26 により 2026-09-24 訂正）: Rolust に登録済みの IAM ユーザが Rolust の外で手動により信頼ポリシーへ追加されていた場合、警告表示ではそのユーザは「管理下」と判定されるため、管理外 principal の警告に出ない。反映処理は凍結入力に名前が挙がった principal しか触らないため、そのユーザが凍結入力の削除対象に入らない限り信頼ポリシーに残る。訂正前は「申請で未チェックであれば反映時に削除される」としていたが、反映処理の管理下を凍結入力とした決定（上の注記）により、この帰結は成り立たない。

**登録時の取り込みの帰結**（Issue #80 により 2026-09-30 追記。Issue #135 により 2026-10-07 訂正。訂正前は「紐づけ時の取り込みの帰結」）: ロールを登録するとき、信頼ポリシーにいるパスなしの IAM ユーザは当該 UserPool の IamUser に取り込まれる（FR-2.1）。定義（全 IamUser の ARN 集合）は変えないので、取り込んだユーザは管理外 principal として警告されなくなる。パス付きのユーザ・ロール・サービス・root・ワイルドカード・Deny の principal は取り込まれず、警告のままである。ロールの削除は IamUser を消さず、削除したロールは申請から開く差分確認画面に現れないので、この警告の対象外になる。既存のロール（Issue #135 より前に紐づけたもの）は取り込み直されない。取り込み直すには、削除して登録し直す。

**ChangeRequest の記録範囲と凍結方式の帰結**:

1. 信頼ポリシー全文の before / after を保存しないため、反映後に Rolust 以外の手段で信頼ポリシーが変更されると、保存された入力から再算出した差分は当時の実際の差分と一致しないことがある。 [Q13]
2. FR-4.2 の警告内容（検出された管理外 principal）を ChangeRequest に保存しないため、「警告を見たうえで反映した」という事実は監査記録に残らない。残るのは反映したという事実のみである。 [Q13][Q3]
3. 実行者は、ChangeRequest の作成者（`createdBy`）と反映者（`appliedBy`）だけを記録する（Issue #120 により 2026-10-05 訂正。訂正前は「実行者を記録しないため、監査記録は『いつ・何を』までであり『誰が』は残らない。将来 管理者エンティティを導入する時点で追加する」とした）。Assignment のセルを誰が変更したか、誰が破棄したかは残らない。Issue #120 より前に作られた申請と、実行者を特定できなかった操作は「誰が」が空になる。`basic` では単一の資格情報なので、実行者は常に同じ名前になる。管理者エンティティの導入は引き続き将来の課題である。 [Q15][Q5][A-6]
4. **ChangeRequest の入力は凍結されるため、未反映の申請が存在する間に Assignment を変更すると、両者は乖離する。** 反映されるのは凍結された申請の内容であり、凍結後の Assignment 変更は次の申請で反映される。FR-4.6 により当該ロールは新規申請の対象から除外されるため、管理者は**既存の未反映申請（状態が「下書き」または「失敗」）**を反映または破棄してからでないと新しい変更を申請できない。失敗した申請を放置すると当該ロールの新規申請がブロックされ続ける点に注意する。 [Q18][Q24][Q26]

**FR-5.8 の範囲**（Issue #121 により 2026-10-06 追記）: 排他するのは ChangeRequest の状態遷移だけである。Assignment の同じセルの同時更新は後勝ち（セル単位の即時保存・楽観的更新をしない決定による）。Rolust の外からの IAM 変更は、IAM に条件付き更新が無いので防げない。1 ロールの未反映申請は 1 件（FR-4.6）なので、別々の申請どうしの競合は FR-4.6 が防ぐ。

**FR-5.1 の管理下の範囲**（Issue #26 により 2026-09-24 追記）: 保全方式で「そのまま残す」Rolust 管理外の principal は、対象 ChangeRequest の凍結入力に名前が挙がっていない principal すべてである（FR-4.2 の定義の後の注記）。

**FR-5.1 のプレースホルダ**（Issue #16 により 2026-09-25 追記）: IAM の信頼ポリシーは Statement 0 件を受け付けない。そのため反映で Statement が 0 件になるとき、システムは誰も引き受けられないプレースホルダ Statement（`Sid: RolustPlaceholder`。Allow と恒久的に偽の条件の組み合わせ）を挿入する（`docs/guide/managed-roles.md` の「信頼ポリシーは「空」にできない」（Issue #178 により 2026-10-18 訂正）、`packages/core/src/merge.ts` の規則 5）。追加を 1 件以上反映するときは、プレースホルダを取り除く（規則 6）。
- **識別は Sid だけで行う**。中身が手で書き換えられていても Rolust のものとみなすため、プレースホルダは保全の対象ではない。プレースホルダの Statement に手で書き加えた principal は、次の追加の反映で Statement ごと消える。

**FR-5.1 の Sid の重複**（Issue #194 により 2026-10-24 追記）: 追加を収める Rolust 専用 Statement（`Sid: RolustManagedPrincipals`。`packages/core/src/merge.ts` の規則 3）は、その Sid を持つ Statement が既にあっても、採用できる形（`Allow` で、`Condition` と `NotPrincipal` を持たず、`sts:AssumeRole` を許す）でなければ採らない。このとき**同じ Sid の 2 つ目を作らず、反映を拒否する**。IAM はポリシー内の Sid の一意性を要求するため、重複した文書は `MalformedPolicyDocument` で拒否され、そのロールは人が信頼ポリシーを直すまで反映できなくなる。しかも原因は AWS のエラー文からは読み取れない。拒否は、何が・なぜ・どう直すかを含む文言で、反映では状態「失敗」として記録し、差分確認でも反映を指示する前に同じ理由を示す（差分は同じマージを通る。FR-4.1 のプレースホルダの注記と同じ構造）。採用できる形であれば、従来どおりその Statement に追加する。
- **管理外の Statement が残る場合は挿入しない**。IAM はその文書を受け付け、ロールは管理外の principal によって引き受けられる状態のままである。これが正しい状態であり、プレースホルダを足しても何も表さない。

**FR-5.7 の例外**（Issue #26 により 2026-09-24 追記）: ロール登録（FR-2.1）は `iam:ListRoleTags` を呼び、存在しないロールを拒否する。これは FR-5.7 と C-4 を意図的に破る（FR-2.1 の注記、code-generation の質問 11 = A）。ほかのマトリクス操作は IAM を呼ばない。ロール登録は、タグ検証の後に、信頼ポリシーも読む（Issue #79・#80 により 2026-09-30 訂正。Issue #135 により 2026-10-07 訂正。訂正前は、ロールの紐づけを除く、としていた。下の注記）。

**FR-5.7 の例外（登録時）**（Issue #79・#80 により 2026-09-30 追記。Issue #135 により 2026-10-07 訂正。訂正前は「紐づけ時」）: ロールの登録（FR-2.1）は、タグ検証の後に、ロールの信頼ポリシーを `iam:GetRole` で読む（CRUD 系統。`packages/api/src/services/role-import.ts`）。デプロイ先と別アカウントのロールは、ターゲット側の Reader を引き受けて読む（Issue #85 により 2026-09-30 訂正。引き受けの `sts:AssumeRole` も、AWS へ問い合わせる時点を増やさない: 登録時のタグ検証と信頼ポリシーの読み取り、差分確認、反映のいずれかの中で呼ぶ）。AWS へ問い合わせる時点が、信頼ポリシーの読み取り・更新とロール登録時のタグ検証と、登録時の信頼ポリシーの読み取りである（登録の中だけで呼ぶ）。IAM ユーザ／ロールの一覧取得は引き続き行わない。読み取りはロールの実在を確かめる副作用を持ち、存在しないロール（`NoSuchEntity`）の登録は 400 で拒否する。読み取り専用で、CRUD 系統は `iam:UpdateAssumeRolePolicy` を持たない（`iam-policy-design-note.md` 3.10）。（訂正前は、デプロイ先と別アカウントのロールは、IAM を呼ばずに、取り込みなしで紐づけた。FR-2.2 の注記の単一アカウント構成による。Issue #85 により 2026-09-30 訂正。）

**FR-5.7 の例外（乖離の確認）**（Issue #170 により 2026-10-15 追記）: 利用者の指示による乖離の確認（FR-4.9。`GET /api/drift`）は、登録済みの全ロールの信頼ポリシーを `iam:GetRole` で読む（Diff 系統。別アカウントのロールはターゲット側の Reader を引き受けて読む。引き受けの `sts:AssumeRole` も、この確認の中で呼ぶ）。AWS へ問い合わせる時点に、「乖離の確認の指示時」が加わる。読むのは信頼ポリシーだけで、IAM ユーザ／ロールの一覧取得や実在検証ではない。読み取り専用で、実行ロールの IAM ポリシーは増えない（`iam-policy-design-note.md`）。

**FR-5.7 の例外（乖離を直す操作）**（Issue #172 により 2026-10-16 追記）: 乖離を直す操作（FR-4.10・FR-4.11。`POST /api/drift/restore`・`POST /api/drift/adopt`）は、指示の時点で、対象の 1 ロールの信頼ポリシーを `iam:GetRole` で読み直して乖離を再計算する（乖離の確認（FR-4.9）と同じ読み取り。Diff 系統。別アカウントのロールはターゲット側の Reader を引き受けて読む）。ただし FR-4.11 は、未反映の申請があるロールでは信頼ポリシーを読む前に拒否する。AWS へ問い合わせる時点に「乖離を直す操作の指示時」が加わるだけで、読むのは信頼ポリシーだけである。どちらの操作も信頼ポリシーを書き換えない（信頼ポリシーを更新するのは、`apply` 系統の反映だけ）。実行ロールの IAM ポリシーは増えない（`iam-policy-design-note.md`）。

**FR-5.1 の受け入れ基準（Given/When/Then）** — 本要件はブラストラディウスが最大のため BDD 形式で明示する。形式は inception フェーズ規約の `## User Stories`（"User stories follow Given/When/Then (BDD) format for acceptance criteria"）に倣う。 [phase:inception]

```
Given  対象 IAMロールの信頼ポリシーに、Rolust 未登録の principal X が含まれている
  And  当該ロールの下書き ChangeRequest には、追加ユーザとして A のみが凍結されている
When   管理者が当該 ChangeRequest の反映を指示する
Then   更新後の信頼ポリシーには A と X の両方が含まれる
  And  X に関する記述（Condition を含む Statement 全体）は更新前と等価である
  And  当該 ChangeRequest の状態が「反映済み」になり、反映時刻が記録される
```

```
Given  対象 IAMロールの信頼ポリシーにユーザ B が含まれている
  And  当該ロールの下書き ChangeRequest には、削除ユーザとして B が凍結されている（B は Rolust 管理下）
When   管理者が当該 ChangeRequest の反映を指示する
Then   更新後の信頼ポリシーから B が削除されている
```

```
Given  下書き ChangeRequest の作成後に、管理者が同じ IamRole のマトリクスでユーザ C をチェックした
  And  当該 ChangeRequest には C が含まれていない
When   管理者が当該 ChangeRequest の反映を指示する
Then   更新後の信頼ポリシーに C は含まれない
  And  ChangeRequest の記録内容と実際に反映された内容が一致する
```
